# HomenS.AI JobPilot — архитектура

[English](../../ARCHITECTURE.md) | [Русский](ARCHITECTURE.md)

09.10.2026 · Автор идеи и разработчик: Serhii Khomenko / HomenS.AI · https://homensai.com/ · документация CC BY-NC 4.0.

Статус: проектная и эксплуатационная спецификация; была ли опробована каждая процедура, записано в ACCEPTANCE_TESTS.md. Никаких серверов, Docker или SQL.

## 1. Основное решение: правила и файлы

Система — это **ИИ-агент** (Codex или Claude Code), **письменные правила**, **папка данных** и локальный вид статистики. Агент ищет, пишет документы, разговаривает с человеком и хранит каждую запись в читаемом файле (JSON, JSONL, Markdown, документы). HTML-страница не отдаёт команд; её данные меняются только тогда, когда работает агент.

Защитные меры (лимит 44, никогда не отправлять дважды, один писатель, ничего не отправляется без разрешения) — это *процедуры, которым следует агент*, а не технические замки. Поэтому каждое правило — контрольный список, выполняемый перед действием; по умолчанию только черновики; автоматическая отправка требует письменного подтверждения человека, что лимит и защита от повторов тогда зависят от агента; а сценарии приёмки (ACCEPTANCE_TESTS.md) проверяются вручную на вымышленных данных до любой реальной отправки.

## 2. Части и ответственность

| Часть | Что делает агент | Где хранится |
|---|---|---|
| Рабочая папка, возможности | Папка, формат, человек, профиль; проверяет каждый инструмент (раздел 7) | `workspace.json` |
| Профиль и база знаний | Материалы и интервью → предложенные → подтверждённые факты с источниками; профиль поиска | `Life_Story.md`, `profile.json` |
| Поиск, планирование | Цели (дубликаты, свежесть, радиус, маршруты); слоты, резервы, переносы | `registry.json`, журнал |
| Документы | Пакеты из требований и подтверждённых фактов, версии, визуальная проверка | папка заявки |
| Почта | Треды целиком, доказательство отправки, уведомления, ответы | журнал, `Status.txt` |
| Отчётность | Подсчёт на фиксированной позиции журнала; DOCX/PDF/HTML с одними и теми же цифрами | `reports/`, `dashboard/` |

Изменения состояния сначала записываются в журнал. Какой файл агент читает и когда: `AGENTS.md`.

## 3. Единица учёта — человек

`person_id` объединяет направления поиска одного человека. У каждого направления свой `profile_id`, языки документов, учётная запись, документы и согласия. Квота и проверки повторных заявок общие по `person_id`; у разных людей отдельные журналы.

```text
Local_Data/
  workspace.json  # workspace_id, format, language, stage of the first run, capabilities
  Put_Here/  # the ONLY place where the person puts things; the agent only reads it
    1_My_Documents/  # CVs, diplomas, certificates, references (originals)
    2_My_Story/  # the person's story: transcripts, notes, interviews, the questions
    3_Report_Template/  # optional report template
    4_CV_Templates/  # everything about the CVs, any format; read only
    5_Cover_Letter_Templates/  # everything about the cover letters; read only
  persons/<person_id>/
    Knowledge_Base/Life_Story.md  # the knowledge base: confirmed facts of the life story
    journal/transactions-YYYY-MM.jsonl  # the only authoritative journal; monthly segments, -pN parts above 500 lines
    journal/writer.lock  # exists only while one chat is writing
    state/person.json  # person, profile list, setup_progress
    state/quota.json  # monthly counters, rebuilt from the journal
    outbox/<send_attempt_id>/  # prepared send package, never edited
    runs/  # person-level session notes (first setup)
    archives/  # local archives (DATA_CONTRACT.md §11)
  Resume/  # CV drafts and the Word copy of the template in use; one subfolder per person_id with several people
  CoverLetter/  # the same for cover letters
  profiles/<profile_id>/
    profile.json  # current confirmed configuration
    registry.json  # targets, applications, queue (projection)
    runs/  # session notes: plans, results, questions
    reports/<YYYY-MM>/  # report revisions and manifests
  Applications/<YYYY>/<MM_Month>/  # one tree for all years, e.g. 2026/10_October/
    001_Muster-Maschinenbau_Stuttgart_Maintenance-technician/  # number, company, city, role
      Company.md · Resume_v001.docx/.pdf · CoverLetter_v001.docx/.pdf · EmailText_de.txt · EMAIL_TO_SEND.txt
      Status.txt  # append-only history of this application
      Replies.txt  # every reply and delivery notice in full
  dashboard/
    index.html  # local menu: statistics and readiness per profile
    profiles/<profile_id>/summary.js · index.html · readiness.html  # data; unchanged template copy; readiness page
  Archive/<YYYY-MM-DD>_daily/  # daily full archive of Local_Data, for a USB stick (DATA_CONTRACT.md §11.9)
```

`Local_Data` — технический путь во всех языковых редакциях; у панели один путь, `Local_Data/dashboard/`; идентификаторы профилей уникальны. Каждая строка журнала несёт `person_id` и, где это применимо, свой профиль; перед действием агент проверяет, что профиль принадлежит этому человеку и этой учётной записи.

**Изоляция людей и профилей (процедура, F12).** У каждого человека есть `persons/<person_id>/` и оригиналы в `Put_Here/<name>/`; агент никогда не открывает оригиналы, базу знаний, журнал, состояние, outbox, архивы или почту другого человека. Новый человек проходит TODO_FOR_AI.md, Часть A, начиная с A2 (A1, проверка рабочей папки, не повторяется); его ход настройки — `setup_progress` в `persons/<person_id>/state/person.json` с теми же словами этапов, а `stage` в `workspace.json` описывает только настройку рабочей папки первым человеком. Согласия, квота, учётные записи и представления по людям: DATA_CONTRACT.md §17. Это изоляция процедурой, а не граница операционной системы.

## 4. Одна строка на завершённое действие

Журнал — это набор месячных текстовых файлов (правило 8) с одним объектом JSON на строку. Строка пишется, когда действие **завершено**: `schema_version`, `sequence` (1, 2, 3 … без пропусков), `action_id`, `person_id`, `recorded_at`; список `events`, у каждого события свой уникальный `event_id`; и короткий текст `result`, которого достаточно, чтобы повторить ответ, если то же действие запросят снова.

Правила для агента:

1. **Только дописывать.** Старая строка никогда не правится и не удаляется; исправление — новая строка, называющая событие, которое она заменяет (`supersedes_event_id`).
2. **Перед записью:** прочитайте последнюю строку, возьмите следующий `sequence` и проверьте, что этого `action_id` нет ни в одном сегменте. Если есть, сообщите прежний результат и больше ничего не делайте.
3. **Пишите строку целиком за один раз**, затем обновите представления (реестр, очередь, `Status.txt`, `quota.json`, статистику). Если чат остановится посередине, следующий чат их пересоберёт (6b).
4. **Повреждённая или недописанная последняя строка** никогда не исправляется молча: остановитесь, сохраните файл, скажите человеку, восстанавливайте по последней полной строке и доказательствам из почты.
5. **Один писатель за раз** (4b). Чужая блокировка означает: остановиться и спросить. Блокировка защищает, только если каждый чат следует протоколу и эксклюзивное создание работает; иначе работает один чат за раз.
6. Решение о квоте или отправке всегда заново читает журнал; сводке из более ранней части чата никогда не доверяют.
7. **Считайте инструментом системы, а не на глаз.** Использованные, зарезервированные и непроверенные слоты месяца считаются текстовым поиском полей месяца в событиях квоты во всех сегментах (формулы: DATA_CONTRACT.md §3c, свободный остаток: DATA_CONTRACT.md §5; команды: §4a). Агент показывает число и способ, которым оно найдено, и сравнивает его с `quota.json`; при расхождении или отсутствии файла прав журнал, и `quota.json` пересобирается (`examples/quota.example.json`).
8. **Запись строки (один способ дописывания, месячные сегменты).** Текущий сегмент — `journal/transactions-YYYY-MM.jsonl` местного месяца человека или его часть `journal/transactions-YYYY-MM-pN.jsonl`, когда в месяце 500 строк (DATA_CONTRACT.md §3c); закрытый сегмент никогда не правится. Сегменты, файл блокировки и файлы JSON — UTF-8 без BOM, только с окончаниями строк LF, и заканчиваются ровно одним LF. JSON не склеивается вручную; текст не пишется перенаправлением оболочки или heredoc; точная замена файловым инструментом используется только для шага 3.
   1. **До записи.** Под блокировкой записи найдите текущий сегмент (при 500 строках следующая часть `-p2`, `-p3` … — новый сегмент). Прочитайте его последнюю строку, она должна быть полной; если сегмент новый или пустой, прочитайте последнюю строку самого нового предыдущего сегмента (для самой первой строки `n` равно 0). Возьмите `n`, её `sequence`; проверьте, что нового `action_id` нет ни в одном сегменте. Запишите в заметку запуска: число строк; последнюю строку `L` без перевода строки (она уникальна: несёт свой `sequence` и `action_id`); `S0`, размер сегмента в байтах; и `C0`, SHA-256 всего сегмента (новый сегмент: `S0` 0, `C0` — SHA-256 пустого файла, `e3b0c442…b855`). Проверьте, что файл кончается на LF, не содержит CR и BOM.
   2. **Соберите** новую строку `N` в порядке ключей из DATA_CONTRACT.md §3c с `sequence` n+1: один объект JSON на одной строке, идентификаторы как в DATA_CONTRACT.md §2. Неудачная проверка останавливает работу (шаг 5).
   3. **Допишите.** (a) Сегмент со строками: замените `L` на `L`, перевод строки и `N` точной заменой файловым инструментом (для очень длинной `L` достаточно уникального хвоста). Если `L` найдена не ровно один раз, остановитесь. (b) Новый сегмент: проверьте, что файла нет, затем создайте его файловым инструментом ровно с `N` и переводом строки. (c) Сегмент короче 300 строк можно вместо этого записать целиком файловым инструментом: строки, прочитанные на шаге 1, затем `N` и перевод строки; это единственная перезапись сегмента целиком.
   4. **Обратное чтение.** (a) `N` разбирается и имеет `sequence` n+1; строка перед ней, если есть, побайтно совпадает с `L`. (b) Число строк выросло ровно на одну. (c) SHA-256 первых `S0` байт равен `C0` (ни один прежний байт не изменился), а новый размер равен `S0` + байты `N` + 1. (d) В конце по-прежнему LF, нет CR, нет BOM. Запишите значения в заметку запуска.
   5. **Сбой.** Любая неудачная проверка останавливает запись: сохраните сегмент, не обновляйте представления, не выполняйте внешних действий, сохраните блокировку, скажите человеку (правило 4). Прежние строки никогда не переписываются ради исправления.
   6. **Освобождение.** Только после того, как шаг 4 пройден: прочитайте блокировку, проверьте `lock_id` этого чата, удалите её (4b).

### 4a. Команды, которые может использовать агент

Только команды, которые уже есть в системе, набранные прямо в строке; скрипты не сохраняются, а Python — только инструмент аудита тестировщика. Кроме таблицы: просмотр и создание папок, `cmp` или `diff` только для чтения (например, чтобы проверить, что рассказ сохранён слово в слово), и собственные временные файлы агента. Файлы JSON и текстовые файлы (Status.txt, Company.md, заметки запусков, EMAIL_TO_SEND.txt) пишутся файловым инструментом, никогда не перенаправлением оболочки, heredoc, `sed` или подобными средствами; строка журнала — только по правилу 8. Исключения: создание `writer.lock`, копирование в `outbox/`, инструмент документов и однократное разделение старого журнала (DATA_CONTRACT.md §3d), которое копирует байты по диапазонам строк и проверяется обратным чтением по контрольной сумме.

| Что нужно | Linux / macOS | Windows PowerShell |
|---|---|---|
| Время UTC | `date -u +%Y-%m-%dT%H:%M:%SZ` | `(Get-Date).ToUniversalTime().ToString("yyyy-MM-ddTHH:mm:ssZ")` |
| UUID | Linux `cat /proc/sys/kernel/random/uuid`; macOS `uuidgen \| tr 'A-Z' 'a-z'` | `[guid]::NewGuid().ToString()` |
| Текущий местный месяц | `TZ=Europe/Berlin date +%Y-%m` (зона IANA человека) | `[TimeZoneInfo]::ConvertTime([DateTimeOffset]::UtcNow,[TimeZoneInfo]::FindSystemTimeZoneById('W. Europe Standard Time')).ToString('yyyy-MM')` (зона IANA, сопоставленная с именем Windows) |
| Контрольная сумма (`C0`) | Linux `sha256sum '<file>'`; macOS `shasum -a 256 '<file>'` | `(Get-FileHash -Algorithm SHA256 -LiteralPath '<file>').Hash.ToLower()` |
| Размер в байтах (`S0`) | `wc -c < '<segment>'` | `(Get-Item -LiteralPath '<abs path>').Length` |
| Контрольная сумма первых `S0` байт (правило 8, 4c) | Linux `head -c <S0> '<segment>' \| sha256sum`; macOS `head -c <S0> '<segment>' \| shasum -a 256` | `$b=[IO.File]::ReadAllBytes('<abs path>'); -join ([Security.Cryptography.SHA256]::Create().ComputeHash($b,0,<S0>) \| ForEach-Object { $_.ToString('x2') })` |
| Байты последней строки с её LF (4c) | `tail -n 1 '<segment>' \| wc -c` | `[Text.Encoding]::UTF8.GetByteCount((Get-Content -Encoding UTF8 -LiteralPath '<abs path>' -Tail 1)) + 1` |
| Кончается на LF, нет CR, нет BOM | `tail -c 1 '<segment>' \| od -An -c` показывает `\n`; `tr -cd '\r' < '<segment>' \| wc -c` равно 0; `head -c 3 '<segment>' \| od -An -tx1` не `ef bb bf` | с `$b`, как выше: `$b[-1] -eq 10; @($b -eq 13).Count -eq 0; -not ($b[0] -eq 0xEF -and $b[1] -eq 0xBB -and $b[2] -eq 0xBF)` |
| Последние строки, число строк | `tail -n 1 '<segment>'`, `tail -n 2 '<segment>'`; `wc -l < '<segment>'` | `Get-Content -Encoding UTF8 -LiteralPath '<segment>' -Tail 1` (или `-Tail 2`); `(Get-Content -Encoding UTF8 -LiteralPath '<segment>').Count` |
| Число совпадений месяца (правило 7) | `grep -oE '"consumed_month" *: *"2026-10"' <journal> \| wc -l` (никогда `grep -c`: он считает строки, а не совпадения) | `(Select-String -Encoding UTF8 -Path <journal> -Pattern '"consumed_month"\s*:\s*"2026-10"' -AllMatches \| ForEach-Object { $_.Matches.Count } \| Measure-Object -Sum).Sum` (пусто означает 0) |
| Каждая строка — корректный JSON | Обратное чтение файловым инструментом: один объект на строку; `jq empty '<segment>'` только если jq установлен | `Get-Content -Encoding UTF8 -LiteralPath '<segment>' \| ForEach-Object { $_ \| ConvertFrom-Json } \| Out-Null` |
| Создать `writer.lock` с содержимым, с отказом, если он существует | `set -C; printf '%s\n' '<lock json>' > '<absolute path>/journal/writer.lock'` (bash или zsh) | `` $f=[IO.File]::Open('<absolute path>','CreateNew','Write','None'); $w=New-Object IO.StreamWriter($f,(New-Object Text.UTF8Encoding($false))); $w.Write('<lock json>'+"`n"); $w.Close() `` |
| Копировать в `outbox/<send_attempt_id>/` | `cp '<source>' '<outbox folder>/'`, затем контрольная сумма каждой копии | `Copy-Item -LiteralPath '<source>' -Destination '<outbox folder>'`, затем контрольная сумма каждой копии |
| DOCX → PDF | Сначала инструмент документов платформы; иначе `soffice --headless --convert-to pdf --outdir '<folder>' '<file.docx>'` | то же |

`<journal>` — все сегменты `journal/transactions-*.jsonl` человека; `<segment>` — текущий. Пути абсолютные и в кавычках. Состояние оболочки не сохраняется между командами, поэтому `set -C` и создание блокировки — одна команда; JSON блокировки не содержит апострофа. Формы для Linux опробованы с bash и GNU coreutils; формы для macOS — их аналоги BSD. Формы PowerShell ещё не опробованы на настоящей машине с Windows; первая проба входит в проверки приёмки.

### 4b. Протокол блокировки записи (F07)

**Охват.** Одна блокировка на человека, `persons/<person_id>/journal/writer.lock`, для журнала, квоты и событий профиля этого человека. Она охватывает только шаги записи; поиск, отрисовка и внешние вызовы происходят вне её. Блокировка другого человека не блокирует и не разрешает записи этого человека.

**Взять блокировку.**

1. Создайте файл **вместе с содержимым одной командой**, которая завершается неудачей, если файл существует, с абсолютным путём (§4a). Проверить, что файла нет, и потом создать его — это не эксклюзивное создание.
2. Содержимое — одна строка JSON с `lock_id`, `run_id`, `owner`, `person_id` и `created_at` (DATA_CONTRACT.md §3c, «Файл блокировки»); `run_id` есть и в заметке сессии чата.
3. Если файл существует, ничего не пишите и прочитайте его. Его `run_id` — этого чата: продолжайте (перезапущенный чат узнаёт свою блокировку по своей заметке). Иначе: остановитесь, сообщите `LOCK_HELD`, спросите человека. **Пустая или нечитаемая блокировка** (владелец остановился между созданием и записью) — чужая блокировка: применяется процедура для устаревшей блокировки.
4. Перед каждой записью снова прочитайте блокировку и подтвердите `lock_id`; если она исчезла или изменилась, откажитесь от записи и сообщите об этом.
5. `capabilities.writer_lock` в `workspace.json` фиксирует, работает ли эксклюзивное создание (`available`, `unavailable`, `unknown`). Папки с облачной синхронизацией (OneDrive, iCloud, Dropbox) не дают эксклюзивного создания между устройствами: `unavailable`. Если не `available`, агент не заявляет об эксклюзивности, не выполняет автономных параллельных записей или внешних действий и говорит человеку, что работать может только один чат.

**Освобождение блокировки.** Только владелец и только после того, как его последняя строка прошла обратное чтение по правилу 8, шаг 4 (чат, который ничего не записал, освобождает после последней проверки): прочитайте блокировку, подтвердите свой `lock_id`, удалите её отдельным шагом. Неудачная запись оставляет блокировку и останавливает чат; блокировка никогда не удаляется той же командой, что и запись, которая могла не удаться. Никогда по возрасту, другим чатом или по тайм-ауту; строки журнала нет.

**Устаревшая блокировка.** Блокировка никогда не истекает по возрасту, а её удаление никогда не освобождает резерв. Блокировка, которая не принадлежит этому чату, удаляется только после следующего, в таком порядке: (a) человек подтверждает, что чат-владелец больше не работает; (b) последняя строка журнала — полный JSON, а в `sequence` нет пропусков (DATA_CONTRACT.md §3c); (c) каждая открытая попытка (`send_started` или намерение планирования без результата) перечислена и становится `send_uncertain`, если не сверена с SENT или «Запланированными», а папки outbox без результата перечислены; (d) удалённое состояние проверено, где это позволяет инструмент почты; что нельзя проверить, остаётся открытым; (e) блокировка удалена, это отмечено в записи запуска и в `result` следующей строки журнала (не отдельное событие). Пока есть открытая попытка, никакая новая отправка или планирование для этого человека не разрешены ни в одном чате.

**Точки сбоя.** Ни одна из них не делает второго внешнего вызова.

| Точка сбоя | Что остаётся | Восстановление |
|---|---|---|
| До создания блокировки | Ничего | Начать заново |
| Блокировка создана (в том числе пустая), строка не записана | Только блокировка | Проверка устаревшей блокировки; внешнего вызова не было; удалить после (a) |
| Во время записи строки | Возможно, обрезанная последняя строка | Остановиться, сохранить файл (правило 4); разбираться по последней полной строке |
| После строки намерения (`quota_reserved`, `send_started`): до вызова, ответ потерян или до строки результата | Открытая попытка; вызов мог произойти | Один раз сверить SENT и «Запланированные»: проверено → `sent_verified` + `quota_consumed` (или запись о планировании); доказано отсутствие → `failed_before_send` + `quota_released`; иначе `send_uncertain`, резерв сохраняется, решает человек. Никогда не вызывать снова |
| После строки результата, до представлений | Представления устарели | Повторное воспроизведение (6b); без внешних действий |
| Два чата борются за последний слот | Одно эксклюзивное создание удаётся | Проигравший ничего не пишет, `LOCK_HELD`; проверка квоты выполняется после взятия блокировки |
| Блокировка удалена кем-то другим во время записи | Запись может остановиться посередине | Шаг 4 останавливает запись; следующий чат следует процедуре для устаревшей блокировки |

Без эксклюзивного создания эти правила всё равно действуют, а параллельные чаты для одного человека вообще не поддерживаются.

## 5. Стандартные действия

Агент выполняет именованные действия, каждое — контрольный список в `TODO_FOR_AI.md`, Часть C, и использует эти названия в журнале и в сообщениях: Inspect workspace; Resume work; Propose / confirm profile; Import targets; Register package; Plan queue (только предварительный просмотр); Commit plan (план и резервы после принятия); Send check («разрешено» или «заблокировано», ничего не отправляется); Send (одна разрешённая отправка и её результат); Read / classify / reconcile mail (с доказательством, никогда не отправляя повторно); Replay / rebuild views (6b); Build report / statistics (одни и те же цифры); Backup / restore check и Create local archive (R01, раздел 12); Schedule in Gmail (R03, 6a; ещё не отправлено); Plan the month and cadence (R02, R04; 8a, 8b); Daily check at 16:00 (R05, 8c).

Каждый ответ называет результат (`ok`, `needs_input`, `conflict`, `blocked` или `failed`), код причины, позицию в журнале, файлы и следующий шаг. Коды причин и какие действия пишут строку: DATA_CONTRACT.md §3c (например, `ACCOUNT_MISMATCH`, `QUOTA_EXHAUSTED`, `SEND_UNCERTAIN`, `PACKAGE_CHANGED`, `SUBJECT_TOO_LONG`, `MODE_DRAFT_ONLY`, `LOCK_HELD`). Пройденная проверка перед отправкой — не постоянное разрешение: Send снова проверяет позицию журнала, время, согласие и пакет.

## 6. Отправка и outbox

Outbox `outbox/<send_attempt_id>/` хранит для одной попытки копии прикладываемых файлов, `message.txt` (получатель, тема и текст точно в том виде, как они отправляются) и `attempt.json` (`account_id`, `application_id`, `send_attempt_id`, `consent_id`, контрольные суммы копий); никаких секретов. Попытка с `send_started` и без результата — открытая.

Каждое внешнее действие с почтой (отправка, планирование в Gmail, перенос, отмена) следует TODO_FOR_AI.md, Часть C, «Порядок внешних действий (F07)»: неизменяемый пакет → согласие, привязанное к манифесту → резерв и долговечное намерение → один внешний вызов → сверка → зафиксированный факт. **Жёсткое условие:** строка намерения (`quota_reserved` и `send_started`) пишется под блокировкой, читается обратно по правилу 8 и непосредственно перед единственным вызовом всё ещё должна быть последней строкой текущего сегмента, с `send_attempt_id` и SHA-256 манифеста из одобрения. Если запись или обратное чтение не удались: никакого вызова, больше ничего не записывается, блокировка сохраняется; если не удалась только эта проверка последней строки: никакого вызова, а открытое намерение сверяется (4b). У каждого `send_attempt_id` один исполнитель; повторный запуск сверяет существующую попытку. У пакета один способ передачи (`agent_local_run`, `gmail_scheduled` или `manual_by_person`, DATA_CONTRACT.md §12.1).

**Виды отправки (F01).** У `cv_submission`, `thank_you` и `ordinary_reply` (включая вопрос о сроке) свой ключ повтора, который проверяется в строке, начинающей отправку: DATA_CONTRACT.md §4. Открытая или неопределённая попытка блокирует повтор по её ключу и все новые отправки этого человека.

Внешний вызов и локальная запись не могут быть атомарными: после `send_started` никто не знает, был ли вызван почтовый сервис. Согласие, отозванное до `send_started`, блокирует отправку; после него отправка сверяется, но её отмена никогда не обещается. Отсутствие в SENT при неполной проверке ничего не доказывает.

### 6a. Gmail «Запланированные» через браузер агента (R03)

**Условия.** Режим это разрешает, и человек сам вошёл в нужную учётную запись Gmail в браузере; агент никогда не получает пароли, одноразовые коды или cookies, а сессия может истечь в любой момент. Gmail отправляет запланированное сообщение, даже когда агент не работает, поэтому согласие, календарь, пакет и резерв проверяются до планирования; изменение любого из них требует нового одобрения, а для уже запланированной записи — сначала проверенного изменения или отмены.

**Ограничение встроенного браузера.** В документированной версии он не может загружать файлы. Если эта установка не может приложить одобренные файлы, агент останавливается до планирования и использует ручной путь.

**Шаги и состояния:** TODO_FOR_AI.md, Часть C, «Gmail «Запланированные» через встроенный браузер (R03)», и DATA_CONTRACT.md §12.2. Неизвестный результат — это событие `send_uncertain` (способ передачи `gmail_scheduled`); `schedule_uncertain` — только название этого состояния. Никогда не создавать второе сообщение «на всякий случай».

**Ручной запасной путь.** Без браузера или входа, и если намерение не записано, ничего не планируется, и заявка идёт в TODO_FOR_AI.md, Часть C, «Ручной запасной путь для письма (R20)» (`EMAIL_TO_SEND.txt`): человек сам отправляет или планирует её с той же учётной записи (`manual_by_person`) и сообщает об этом; агент проверяет это в «Запланированных» или SENT. Намерение без проверенного результата сначала сверяется. Ручное планирование использует тот же единственный резерв.

### 6b. Повторное воспроизведение: пересборка представлений (F04)

Каждый производный файл (`registry.json`, очередь, записи `Status.txt`, `quota.json`, `summary.js`, данные готовности и отчётов) можно пересобрать из журнала и неизменяемых файлов; исходные события и идемпотентность: DATA_CONTRACT.md §3d. Повторное воспроизведение никогда не меняет журнал.

1. Скопируйте все сегменты журнала во временное место; в журнал человека ничего не пишется.
2. Проверьте каждую строку: она разбирается, в `sequence` нет пропусков между сегментами, ни один `event_id` или `action_id` не повторяется с другим содержимым (`INTEGRITY_CONFLICT`). Повреждённая или неполная строка останавливает воспроизведение (`JOURNAL_DAMAGED`); ни одно представление не пишется.
3. Примените события в порядке `sequence` (DATA_CONTRACT.md §3d): компании и цели, маршруты, пакеты, планы и переносы, отмены, резервы и квота, согласия, почта и ответы, статусы, архивы.
4. Соберите во временном месте: реестр, очередь, записи `Status.txt`, `quota.json` (правило 7) и `summary.js` с его `source_revision`.
5. Файл, SHA-256 которого отличается от события, ссылающегося на него, помечает зависимое представление `INTEGRITY_CONFLICT`. Воспроизведение не меняет квоту и само не пишет `approval_revoked`; агент записывает `approval_revoked` новой строкой, когда затронут одобренный пакет.
6. Замените каждое отличающееся представление (временный файл, обратное чтение, замена). Проекция, которую нельзя пересобрать, объявляется неполной и никогда не угадывается.
7. Второе воспроизведение с той же ревизии ничего не меняет и не добавляет строки журнала или `Status.txt` для уже записанного `event_id`.

Планы, пакеты, копии в outbox и архивы никогда не правятся. Выпущенный отчёт никогда не переписывается: изменившиеся цифры получают новую ревизию (`report_built`). Отсутствующая версия показывается как «версия отсутствует» и не восстанавливается по памяти; восстановленная копия (раздел 12) может её дать, если совпадает контрольная сумма. `quota.json` получается только из событий; повреждённый или отсутствующий файл заменяется результатом воспроизведения.

## 7. Возможности инструментов агента

Проверенными считаются только платформы, названные в ACCEPTANCE_TESTS.md (Claude Code не подтверждён). При настройке агент проверяет каждую возможность: файловая система, веб-поиск, поиск маршрутов, чтение почты, чтение треда целиком, отправка почты, доказательство отправки (SENT), изображения и сканы, отрисовка DOCX, отрисовка PDF, запланированное пробуждение и блокировка записи (`examples/workspace.example.json`). Он записывает available / unavailable / unknown, время проверки и в своём `note` несекретную версию инструмента, если инструмент её сообщает, в `workspace.json`; строка в файле настроек не доказательство. В каждом чате, который может отправлять, агент определяет учётную запись почты и сравнивает её с профилем, а возможности почты проверяет снова, если их проверка старше 7 дней.

| Недоступно | Работа, которая может продолжаться |
|---|---|
| Gmail | Поиск, профиль, локальные пакеты; статистика почты помечена как непроверенная |
| Отправка или доказательство в SENT | Черновики и чтение; автоматические внешние действия выключены |
| Маршруты | Цель остаётся `route_unverified`; никаких утверждений о требованиях к дороге |
| Отрисовка | Черновики сохранены; визуальная проверка не отмечается как принятая |
| Планирование задач агента | Человек запускает чат вручную; очередь остаётся в файлах |

Для почты агенту нужно определить учётную запись, перечислять сообщения постранично, читать тред целиком, отправлять один раз и находить доказательство отправки; он сообщает, что действительно предлагают его инструменты. Месячный лимит не обеспечивает никто, кроме агента, поэтому запланированная автоматическая отправка по умолчанию выключена и включается только для профиля, человек которого это принял, после того как сценарии отправки проверены в среде этого человека.

## 8. Новые чаты и ежедневный цикл

Состояние хранит журнал; флажок в Markdown ничего не доказывает. Папка без `workspace.json` новая: первичная настройка — TODO_FOR_AI.md, Часть A, её позиция — `stage` в `workspace.json`. Каждый следующий чат следует TODO_FOR_AI.md, Часть B, и заканчивается своей записью о сессии в `runs/` (DATA_CONTRACT.md §18). Прерванный чат не меняет состояние: незаконченные операции остаются в журнале, а статус перечитывается перед каждым внешним действием.

Просмотр почты — цикл по следующему токену из TODO_FOR_AI.md, Часть B, шаг 5 (DATA_CONTRACT.md §15.3). Его позиция сдвигается только после того, как целиком обработанная страница сохранена (повторное чтение безопасно: сообщения различаются по `(account_id, gmail_message_id)`); инструмент, который не умеет продолжать, получает ограниченный повторный просмотр с перекрытием, отмеченный как неполный. Сбой для одного профиля не отмечает другой профиль как проверенный.

### 8a. Ритм отправки (R02)

Значения ритма, `max_per_run`, `max_per_day`, `sending_rule_statement`, `inter_message_delay_minutes`, `dst_rule`, способы передачи, пропущенные слоты (`slot_missed`) и проверка: DATA_CONTRACT.md §13 (календарь: его §7; квота: его §5). Как спрашивать: TODO_FOR_AI.md A7, «Правила ритма (R02)».

### 8b. Подготовка месяца и напоминание (R04)

Месячный план, вопрос и напоминание (`schedule.monthly_reminder_local_time`), шаги подготовки и случай без ответа: DATA_CONTRACT.md §14. Подготовка не расходует квоту; запланированные сообщения её резервируют.

### 8c. Ежедневная проверка в 16:00 (R05)

Регистрация задачи, полнота, постраничное чтение, пропущенные запуски и месячный отчёт в последний рабочий день: DATA_CONTRACT.md §15. Шаги каждого запуска: TODO_FOR_AI.md, Часть B, шаг 6.

## 9. Снимки, отчёты и масштаб

Отчёт считается один раз, на фиксированной позиции журнала; DOCX/PDF и страница статистики несут одни и те же цифры, `source_revision` и дату среза, а анализ рынка не меняет счёт почты. Страница профиля показывает свои заявки и общую квоту человека. Агент пишет только `summary.js` (DATA_CONTRACT.md §9); страница — неизменённая копия шаблона, которая не отдаёт команд и не обращается к Gmail. Индексы, очереди или обработчики не нужны.

## 10. Изменения формата и граница первого выпуска

**Метки версий (у каждого номера одно значение; другие документы ссылаются на эти названия).**
- Версия документации задаётся файлом [VERSION](../../VERSION).
- `schema_version` снимка статистики (`summary.js`) — 1.4 (DATA_CONTRACT.md §9.1).
- `schema_version` настроек (`profile.json`) — 1.4, а `workspace.json` — 1.3 (`examples/settings.example.json`, `examples/workspace.example.json`); `schema_version` файла `quota.json` — 1.3 (`examples/quota.example.json`).
- `format_version` файла `workspace.json` — 1.4: устройство файла рабочей папки (DATA_CONTRACT.md §1).
- `schema_version` строки журнала — 1.2 (устройство строки, DATA_CONTRACT.md §3c); `registry.json` тоже использует 1.2.

Номер меняется только вместе со своим форматом; новые названия событий только добавляются. Папки пользователя никогда не перезаписываются: миграция работает на отдельной копии с отчётом, сохраняет старые ID и записи и требует одобрения человека (журнал в одном файле: «Старый журнал», DATA_CONTRACT.md §3d). Публичные примеры вымышлены.

Первая проба — ручной проход на вымышленных данных: профиль → цель → пакет → план → смоделированный ответ → отчёт и офлайн-HTML; чтение и отправка Gmail идут позже, а тесты прерванной работы и двух параллельных чатов проводятся до любой запланированной отправки. Приёмка требует записанных доказательств (ACCEPTANCE_TESTS.md).

## 11. Четыре языка, один проект

Основной язык — английский; русская, немецкая и украинская редакции лежат в `docs/ru`, `docs/de` и `docs/uk`, с одним контрактом данных, одинаковыми названиями событий и поведением; изменение правила обновляет все четыре. Интерфейс статистики поддерживает `en`, `ru` и `de`; переключение меняет только подписи, а не записи и не отдельно выбранные языки резюме, письма, e-mail и отчёта.

## 12. Локальные архивы и восстановление (R01)

Локальные архивы — это папки в `persons/<person_id>/archives/`, которые пишутся после каждой завершённой операции, когда её факт есть в журнале и представления имеют один `source_revision`. Это резервные копии, никогда не Gmail Archive, и они никогда не меняют почту. Когда, устройство, манифест, шаги записи (`backup_created`, `backup_failed`), срок хранения, нарушение целостности (`ARCHIVE_INTEGRITY_FAILED`), восстановление в отдельную копию и восстановление из Gmail после потери всех архивов (`RECOVERY_MODE`): DATA_CONTRACT.md §11.
