## 1. Зачем нужен проект

**HomenS.AI JobPilot** — автономный рабочий пакет: пользователь скачивает его с GitHub и открывает как локальную папку в Codex или Claude Code. Именно ИИ-агент в чате является исполнителем: читает правила и очередь задач, спрашивает недостающие сведения и разрешения, ищет фирмы/вакансии, ведет локальную базу, формирует документы, проверяет почту в пределах предоставленных подключений и готовит отчеты. Главный продукт — не веб-сервис и не фоновый сервер.

Идея — показать, как сложный рабочий процесс можно организовать через промпты, письменные процедуры, локальные файлы и существующего облачного ИИ-агента, например Codex, без отдельного полноценного приложения для поиска работы. Сначала автор собрал личный процесс на собственном компьютере из папок, документов и промптов в неформальной манере. Когда знакомые рассказали о той же рутинной нагрузке, он решил стандартизировать её. По словам автора, ранний процесс использовался около двух месяцев; на подготовку первой стандартизированной документации ушло примерно два рабочих дня. Это история создания, а не доказательство полной приёмки пакета.

Агент следует правилам, записывает действия в журнал и поддерживает остальные файлы. Лимит 44, защита от повторов и правило одного пишущего — процедуры, а не технические замки. Страница статистики содержит единственный рабочий JavaScript проекта: он проверяет снимок, сортирует и фильтрует данные, но не выполняет внешних вызовов. По умолчанию используется безопасный режим; на любое внешнее действие нужно явное согласие пользователя на точный пакет и расписание.

Единственный рабочий корень — распакованная и явно разрешенная пользователем папка проекта. Внутри нее хранятся инструкции, профили, мастер-биография, исходные материалы, база фирм/вакансий, месячные папки, письма/пакеты заявок, журнал и отчеты. Никакой обязательной отдельной базы на другом диске или центрального сервера нет. Необходимые учетные секреты не записывать в эту папку: использовать защищенное хранилище ОС/провайдера, а в проекте хранить только признак подключения и несекретные метаданные.

Локально открытая папка проекта и один выбранный ИИ-агент (Codex или Claude Code) обязательны. В пакете есть **статическая HTML-страница статистики**: агент обновляет локальный снимок, пользователь просматривает таблицы. Код страницы проверяет снимок и поддерживает сортировку/фильтры; поиск фирм, изменение журнала/очереди и доступ к Gmail ей недоступны. Это обычный локальный файл, а не сервер: Docker, backend и интернет для показа сохранённого снимка не нужны.

Ключевой принцип профиля: система хранит полную подтвержденную биографическую базу человека, а не считает короткое старое резюме полной историей. Пользователь кладёт свои резюме и другие материалы в готовые папки `Положите_сюда` либо просто рассказывает агенту о себе — голосом или текстом, в интервью; агент извлекает/структурирует факты с источниками и подтверждением. Для каждой вакансии он создает короткие релевантные CV и Anschreiben только из подтвержденных фактов. Это самостоятельная авторская разработка Serhii Khomenko; сторонний код из просмотренных GitHub-аналогов не используется.

## 2. Опыт существующих рабочих папок

В рабочих папках нескольких пользователей уже сложились полезные, но неодинаковые практики:

- месячные каталоги и пронумерованные папки работодателей;
- карточки **Company.md** и **Status.txt** в папке каждой заявки, email-тексты, плановые даты и сведения о Gmail;
- разные наборы документов и названия файлов: Anschreiben, Lebenslauf/CV, PDF/DOCX, сведения об отправке;
- отдельные промпты с разными правилами, личными данными, Gmail и разрешениями.

Поэтому существующие корни нельзя просто объединить. Новой системе нужны общий формат данных, отдельная конфигурация каждого пользователя и отдельный безопасный импорт старых папок. Импорт сначала только читающий: исходные каталоги не переименовываются, не перемещаются и не переписываются.

## 3. Архитектура: локальная папка и ИИ-агент

Локальный ИИ-агент и доступная ему распакованная папка — обязательные рабочие части системы. Пользователь выбирает Codex или Claude Code, открывает в нем именно эту папку, создает чат/задачу и говорит «начинай»: агент сам загружает свой файл правил (`AGENTS.md` для Codex, `CLAUDE.md` для Claude Code) и следует `TODO_FOR_AI.md`. Без работающего агента с разрешением на эту папку система не выполняет поиск, учет или обновление статистики. Агент выполняет действия внутри разрешенной папки, отражает прогресс в файлах и обращается к пользователю, если не хватает данных, требуется выбор или новое разрешение. Это не система, которая самостоятельно получает доступ к Gmail или компьютеру только из-за загруженного Markdown.

`TODO_FOR_AI.md` — пошаговый рабочий план: первый запуск — первая настройка (знакомство, проверка инструментов агента, согласие, рассказ человека о себе, документы человека, анализ и база знаний, подтверждение фактов, настройка поиска, почта), продолжение в следующем чате и список проверок для каждого стандартного действия. При первом запуске агент сам ведёт разговор: говорит, что ему нужно, задаёт по одному вопросу и выполняет следующий безопасный шаг. Свою позицию он хранит в `workspace.json` (`stage`).

~~~text
GitHub ZIP → распакованная папка → открыть ее локально в Codex / Claude Code
                                            ↓
                              новый проект/чат/задача
                                            ↓
            README + AGENTS.md/CLAUDE.md + TODO_FOR_AI.md
                                            ↓
ИИ-агент ↔ разрешенная папка проекта (единый источник данных)
  ├─ материалы в Положите_сюда + интервью → база знаний (подтверждённые факты) → профили
  ├─ поиск → проверенные фирмы/вакансии/маршруты → уникальные записи
  ├─ документы и план → CV/Anschreiben → подготовка/разрешенная отправка
  ├─ почта → ответы/DSN → журнал → дневной и месячный отчет
  ├─ обновление локальных данных и генерация статистической страницы из шаблона
  └─ вопрос пользователю, если нужны новые данные/решение/доступ
                                            ↓
                  локальная read-only HTML-страница
                  (год → месяц → таблицы; сортировка)
~~~

### Границы компонентов

1. **Локальный ИИ-агент** выполняет поиск, разбор источников, ведение данных и журналов, подготовку документов/отчетов и разрешенные действия в почте. Весь процесс виден в его чате; пользователю не требуется отдельная система для повседневного управления.
2. **Папка проекта** — единственное место для рабочих данных. JSON хранит проекции, один JSONL-журнал на человека, ведущийся помесячными сегментами, — все первичные операционные события, включая общую квоту и события профилей. Записи ведёт агент по записанному порядку. Части системы, правила журнала, стандартные действия и единый порядок для разных агентов описаны в ARCHITECTURE.md; форматы — в DATA_CONTRACT.md.
3. **Пошаговые инструкции** — `README.md` для человека, `AGENTS.md` для Codex, `CLAUDE.md` для Claude Code и `TODO_FOR_AI.md` с последовательностью действий. Для каждой сессии агент опирается на эти файлы и существующее содержимое, не предполагая, что прошлый чат доступен.
4. **Профиль и база знаний** — мастер-источник фактов внутри папки. База знаний — один Markdown-файл на человека, `База_знаний/Жизнеописание.md` (раздел 4.6, DATA_CONTRACT.md §3a). Агент пишет его по документам человека и по интервью в чате, голосом или текстом; анкета — это интервью, а не форма. Файл остаётся читаемым и доступным для правки человеком.
5. **Обязательная статистическая страница.** Пакет содержит готовый шаблон `dashboard_template/index.html` и рядом с ним файл данных с примерами `summary.js`. Для каждого профиля агент копирует `index.html` **без изменений** в `dashboard/profiles/<profile_id>/` и пишет рядом только файл данных `summary.js`; ещё он обновляет локальное меню `Локальные_данные/dashboard/index.html`. Страница берёт данные из `summary.js` обычным тегом script, поэтому ей не нужны ни fetch локальных файлов, ни сетевые запросы; она не пишет данные и не изменяет очередь. Это frontend для отображения, фильтрации и сортировки. Базовый язык — en; ru выбирается явно и не меняет данные.
6. **Планирование** — ежедневные/периодические действия выполняются новым запуском локального Codex Scheduled task, если эта функция доступна и настроена, либо отдельной сессией агента по инструкции. Статическая страница не запускает агента и не обновляет себя. Никакой Windows-сервис, веб-бэкенд, Docker или сервер не нужен. При расписанных локальных задачах компьютер, приложение и папка должны оставаться доступны; точные условия зависят от агента и версии.
7. **Доступы** — права на локальную папку, веб-поиск, Gmail OAuth/коннектор и Computer Use настраиваются отдельно и только под нужный сценарий. Авторизация и отправка не включаются автоматически из-за распаковки ZIP.

## 4. Профиль человека: база знаний и интервью

### 4.1 Импорт и подтверждение

Во время первоначальной настройки человек распаковывает пакет и открывает эту папку локально в выбранном агенте. В папке уже есть три готовые папки для материалов (раздел 4.6). Человек может заранее положить в них имеющиеся резюме, дипломы, сертификаты, рекомендации и портфолио либо оставить их пустыми и позволить агенту провести интервью. Агент использует только предоставленную рабочую папку, записывает предложенные факты в базу знаний и показывает, из какого файла и места взят каждый факт.

ИИ не считает извлеченный текст подтвержденным автоматически. Пользователь принимает, исправляет или отклоняет каждую предложенную запись. Для факта сохраняются: значение, источник, дата/период действия, статус подтверждения, язык оригинала и ограничения использования. Самооценка пользователя остается самооценкой; ее нельзя представлять как сертификат или проверенную квалификацию.

### 4.2 Темы интервью

Анкета — это интервью, которое агент ведёт в чате по одной теме за раз, в порядке списка ниже. Ответы можно диктовать голосом, они могут быть длинными. Обязательные ответы сведены к минимуму; любую тему можно пропустить, а агент объясняет, зачем она может пригодиться.

- Контакты и местоположение: имя, адрес/регион поиска, допустимое раскрытие контактов.
- Языки материалов: пользователь отдельно выбирает `cv_language`, `cover_letter_language`, `email_language` и `report_language`. Настройки не выводить друг из друга и не определять автоматически по стране или вакансии; язык конкретной подачи можно переопределить с подтверждением пользователя. Если язык не задан, спросить пользователя до генерации.
- Отчет: необязательный шаблон, предоставленный пользователем в `3_Шаблон_отчёта`; оригинал хранить неизменным, результат сохранять отдельным файлом.
- Цель: работа, Ausbildung, практика/Praktikum, Probearbeit, временная работа; профессии и названия должностей; формат занятости, желаемые отрасли и исключения.
- Опыт по каждой станции: работодатель, страна/город, роль, даты, задачи, оборудование/инструменты/системы, команда и зона ответственности, измеримые результаты, достижения, переходы между ролями.
- Образование: школа, профессиональное/высшее образование, специальность, учебные периоды и квалификация; признание диплома, если применимо.
- Курсы, лицензии и сертификаты: название, выдавшая организация, дата, срок действия, уровень/номер, файл-доказательство.
- Языки: язык, отдельные уровни чтения/письма/говорения/понимания, заявленный CEFR и сертификат/дата, если имеется.
- Цифровые, технические и профессиональные навыки: группы навыков, инструмент/технология, уровень, где и когда применялась, доказательство и дата последней практики.
- Проекты, волонтерство, стажировки, внеформальное обучение, публикации и портфолио.
- Сильные стороны и примеры поведения: конкретные ситуации, действия и результат (STAR), командная работа, общение, решение проблем и обучение.
- Пожелания и доступность: что ищем (работа, Ausbildung, практика, Probearbeit, временная работа), где живёт человек, радиус поиска, как человек добирается (машина, поезд, автобус/трамвай, велосипед, пешком — любая комбинация), допустимое время пути, пересадки, пеший участок, вечернее возвращение, график, начало работы и предпочитаемые каналы.
- Вопросы для мотивационного письма: почему эта роль, какие задачи интересны, какой вклад человек хочет внести, чего хочет научиться.
- Файлы и рекомендации: пользователь решает, какие оригиналы/контакты хранить и какие из них можно включать в отдельную заявку.

Интервью принимает свободный текст и длинные устные ответы, даты, повторяющиеся записи (одно место работы за другим) и пропуск темы. После каждой темы агент сохраняет ответы и новые факты, чтобы оборванный чат ничего не потерял.

### 4.3 Безопасность биографических данных

Не собирать по умолчанию религию, семейное положение, сведения о здоровье/инвалидности, национальность, фотографии и другие чувствительные или необязательные данные. Если человек сам добавляет такой факт, пометить его как чувствительный, не использовать в резюме без явного выбора пользователя и не передавать в облачную модель автоматически.

Перед отправкой на внешний ИИ показать, какие факты и документы будут переданы. Предпочтительный режим — передавать только минимальный, относящийся к вакансии набор, а не весь архив. Предусмотреть просмотр, исправление, экспорт, удаление профиля и отзыв почтового доступа.

«Локальное хранение» не означает офлайн-обработку: сведения, которые облачный агент читает инструментом, могут поступать его провайдеру. Согласие на эту обработку нужно получить до первого чтения личных оригиналов, а не после извлечения текста. Без такого согласия агент может работать с обезличенным примером и общими правилами. Всё, что агент записывает по документам или по интервью, сначала имеет статус `proposed`; фактом `confirmed` его делает только подтверждение человека.

### 4.4 Как строится резюме

Мастер-профиль хранит развернутую историю, но резюме — целевая проекция, а не копия всего досье. Система сопоставляет требования вакансии с фактами профиля и может показывать таблицу «требование → подтвержденный факт → источник → куда включено». Пользователь видит пробелы и решает, что уточнить. ИИ запрещено придумывать опыт, работодателей, результаты, сертификаты, уровень языка, даты и право на работу.

По умолчанию язык и оформление выбираются отдельно для каждой подачи. Размер и состав CV адаптируются к стране, работодателю и каналу; развернутая полная анкета остается внутренней базой. Фото необязательно. Все версии получают дату, номер версии, ID профиля и список исходных фактов.

### 4.5 Основание для содержания интервью

База знаний должна быть шире готового CV и строится как редактируемая база жизненного и профессионального опыта. Europass служит одним из ориентиров по полноте мастер-профиля: образование/обучение, опыт, языки, цифровые навыки, проекты, достижения и другие навыки. Система хранит полную мастер-биографию локально, а на выход генерирует только релевантную проекцию под конкретную вакансию и выбранный пользователем язык. Отдельно предусмотрены вопросы о задач и результатов по каждой должности, инструментов/технологий, доказательств, даты актуальности навыка, желаемого направления, мобильности и STAR-примеров; чувствительные данные по умолчанию не собирать.

Эти рекомендации служат ориентиром, а не обязательной формой. Фото и необязательные персональные сведения не требуются; включать их только по выбору пользователя и если это оправдано конкретной заявкой.

### 4.6 Куда человек кладёт материалы и файл базы знаний

В пакете есть готовая папка `Локальные_данные/Положите_сюда/` («положите сюда») с тремя подпапками и короткой инструкцией в каждой. Это единственное место, куда человеку нужно что-то класть руками:

| Папка | Что человек кладёт |
|---|---|
| `1_Мои_документы` | Резюме любых версий, дипломы, сертификаты, рекомендации, официальные письма, портфолио, образцы своих писем; PDF, DOCX, TXT, фото и сканы; сортировать и переименовывать не нужно |
| `2_Рассказ_о_себе` | Рассказ человека своими словами: расшифровка голосовой записи, заметки, ответы на вопросы из файла `Вопросы_для_рассказа.md` (лежит в этой папке); сюда же агент дословно сохраняет интервью как `Интервью_<дата>.md` |
| `3_Шаблон_отчёта` | Только если у человека есть свой образец отчёта |
| `4_Шаблон_резюме` (материалы о резюме) | Всё о резюме человека в любом формате, текущие и старые; только чтение; агент готовит черновики из них и из шаблона, который назовёт человек |
| `5_Шаблон_сопроводительного_письма` (материалы о сопроводительных письмах) | Всё о сопроводительных письмах человека в любом формате; только чтение; то же правило, что для папки 4 |

Папки можно заполнить **до** первого запуска или оставить пустыми. Агент их только читает и ничего в них не меняет, не переносит, не переименовывает и не удаляет. Для второго человека, который пользуется той же папкой, в `Положите_сюда` создаётся подпапка с его именем с теми же тремя подпапками.

**Подготовка рассказа голосом.** Рассказ можно подготовить заранее двумя способами: (а) вне проекта, в любом чате Claude или ChatGPT с голосовым режимом: взять вопросы из `Вопросы_для_рассказа.md`, рассказать, затем попросить ассистента записать рассказ дословно, ничего не добавляя, в текстовый файл и сохранить его в `2_Рассказ_о_себе`; (б) внутри проекта: сказать агенту, что хочется рассказать о себе, — агент ведёт интервью (4.2) и дословно сохраняет каждый ответ. Оба способа дают одинаковый результат.

**База знаний.** По обеим папкам и интервью агент пишет `Локальные_данные/persons/<person_id>/База_знаний/Жизнеописание.md`: всё жизнеописание человека в виде подтверждённых фактов в фиксированном формате (DATA_CONTRACT.md §3a). Затем агент показывает предложенные факты по разделам, и человек подтверждает, исправляет или отклоняет каждый. Заявки и CV используют только подтверждённые факты. Файл написан на языке человека, читается и правится вручную и служит единым источником для всех профилей поиска этого человека.

**Первая настройка по порядку.** Её ведёт агент, а человек только отвечает; формы нет. (1) Куда класть рассказ: если у человека есть написанный рассказ, он кладётся в `2_Рассказ_о_себе`; если нет, агент предлагает подготовить его прямо сейчас, лучше голосом, и дословно сохраняет. (2) Агент просит положить дипломы, сертификаты и другие документы в `1_Мои_документы`. (3) Агент анализирует рассказ и документы и пишет базу знаний. (4) Он спрашивает о пробелах по одной теме, обязательно включая сертификаты, курсы, права, уровни языков, водительское удостоверение и машину. (5) Человек подтверждает факты. (6) Агент спрашивает, что ищем и как: вид поиска, профессии, где живёт человек, радиус, способ добираться и ограничения дороги, предпочитаемые города, четыре языка, ритм отправки; ответы сохраняются как `profiles/<profile_id>/profile.json` (DATA_CONTRACT.md §3b). (7) Почта подключается, только если человек этого хочет. После этого первая настройка завершена, и всё работает по сохранённым файлам. Точные шаги и вопросы — в TODO_FOR_AI.md, часть A.

Работа с шаблоном: исходник сохраняется неизменным; рабочая Word-копия названного человеком шаблона создаётся в `Resume/` или `CoverLetter/` (отдельный редактируемый DOCX), каждая страница сравнивается визуально и результат утверждается до использования. Если конвертация недоступна, агент сообщает об этом и предлагает ручную конвертацию либо согласованное восстановление макета. Пути источника/DOCX, хеши и время проверки сохраняются в профиле; каждая вакансия получает свои файлы. См. раздел «Шаблоны резюме и сопроводительного письма» в [рабочих правилах](OPERATING_REQUIREMENTS.md).

## 5. Географический поиск и единая база

Пользователь выбирает стартовую точку (место, где он живёт), радиус в километрах, способ добираться (машина, поезд, автобус/трамвай, велосипед, пешком — любая комбинация; «общественный транспорт» означает поезд и автобус/трамвай), допустимое время пути, число пересадок, максимальный пеший участок, вечерний возврат и приоритетные города. Система показывает и расстояние по прямой, и фактический маршрут; это разные значения.

Порядок приоритетов хранится отдельно для каждого профиля и не меняется от добавления новых городов. Сначала применяется выбранный радиус и критерий близости к адресу/точке; реальное время и простота маршрута помогают отсеять неподходящие варианты и различить кандидатов, но не должны искусственно опускать более близкую фирму за счет добавленного удаленного города. Расширение географии разрешено после проверки ближней подходящей зоны. Список городов — пользовательский набор, а не универсальный приоритет системы.

Искать фирмы и опубликованные вакансии через разрешенные источники: сайты работодателей, официальные job-порталы и API/поиск, условия которых допускают такое использование. Для каждого результата сохранять URL, название источника, дату/время проверки, локальный адрес/филиал, способ подачи и уровень уверенности. Не заявлять, что список «всех фирм» исчерпывающий: дать оценку охвата, запросов и найденных источников.

Дубликат — не просто повторное имя: учитывать домен, юридическое название, адрес филиала и связь филиалов с головной компанией. Разные филиалы не сливать. Не подавать повторно в фирму, уже отмеченную в реестре, без отдельного решения пользователя.

Рекомендуемая карточка компании содержит:

- имя организации и филиала, адрес и город;
- сайт, email, телефон, контактное лицо/должность;
- типы подходящих ролей и канал подачи;
- требования вакансии/практики и дату актуальности;
- источник каждого контакта и требования, дату проверки, статус подтверждения;
- расстояние, режим транспорта, время, пересадки, пеший участок и источник маршрута;
- историю найденных вакансий, заявок, ответов и отказов.

Если маршрутный источник недоступен, показывать «маршрут не проверен» и не заменять его догадкой. Для вакансий хранить срок публикации/дедлайн и регулярно помечать устаревшие предложения.

## 6. Папки и комплект заявки

Пользователь скачивает GitHub ZIP, выбирает удобное место и распаковывает его. Эту папку он открывает локально в Codex или Claude Code и явно разрешает агенту работать именно в ней. **Все рабочие материалы и создаваемые данные затем остаются внутри распакованной папки**, в подкаталоге данных, исключенном из Git. Агент не создает параллельный каталог на другом диске без явного согласия.

Номер начинается с 001 в каждом месяце. Название каталога не заменяет стабильный внутренний ID компании/заявки. Для текущих пользователей предложить read-only импорт и карту соответствия, но не реорганизовывать их старые каталоги без подтверждения. Все персональные данные под `Локальные_данные/` исключить из Git по умолчанию; публикация рабочих файлов запрещена.

Каталог заявки выбирается по месяцу подготовки и не перемещается при смене плана. Отчеты группируют заявки по фактической дате подачи, независимо от имени каталога. Все пути в записях относительные к корню проекта; после разрешения пути проверять, что он остается внутри этого корня, в том числе при junction/symlink. Сквозную структуру записей и правила Windows-имен см. в DATA_CONTRACT.md.

Если отправка не по email, комплект формируется под канал вакансии: web-форма, портал, бумага, телефон. Не создавать фиктивный email-адрес для вакансии.

**Сопроводительное письмо (R12).** Каждая заявка имеет собственное персональное сопроводительное письмо; оно входит в обязательный комплект и прикрепляется к отправляемым документам, а короткий текст e-mail его не заменяет. Письмо называет правильную фирму, контактное лицо только при подтвержденном наличии, конкретную должность или направление и согласованную дату; оно связывает требования вакансии с подтвержденными фактами (`use: cv`). В нем никогда не бывает названий, обращений или требований другой компании, и оно не выдумывает квалификации, доступность, зарплату или сроки. Если обязательной сведений не хватает, их запрашивают, либо комплект остается непригодным к проверке. Письмо хранится как редактируемый DOCX и проверенный PDF. Во вложения идут утвержденный PDF резюме и утвержденный PDF письма либо один согласованный объединенный PDF с обеими частями полностью; DOCX или черновик по ошибке не прикрепляются. Если работодатель требует другой формат или не принимает письмо, требование фиксируется с источником, а исключение согласуется с пользователем.

**Язык и текст e-mail (R13).** Язык вакансии определяет язык отправляемого e-mail, резюме и сопроводительного письма. Если вакансия его не указывает, агент спрашивает пользователя и предлагает обоснованный вариант; он не угадывает язык по городу, домену или языку страницы. Тело письма следует утвержденной пользователем структуре: обращение, точная вакансия, краткая релевантная мотивация, вложенные документы названы как есть, ясная просьба о разговоре или встрече, утвержденная подпись. Тема — не более 50 символов Unicode после нормализации NFC. Тело никогда не пустое, не содержит незаполненных полей шаблона и текста другой заявки и не утверждает о вложении, которого нет. Перед согласием пользователь видит точный окончательный текст (тему, обращение, тело, подпись) и полный смысловой перевод на язык проверки (`languages.review_language`). Перевод не добавляет опыта, навыков, обещаний или условий и не опускает существенного; он хранится отдельно от отправляемых файлов. Любое изменение текста или языка — новая версия, требующая нового одобрения.

**Даты (R07).** План — единственный источник плановой даты отправки. Одна и та же дата и время стоят в тексте письма, в датируемых полях документов, в `EMAIL_TO_SEND.txt`, в manifest и в записи Gmail Scheduled. Плановая дата и дата документа — разные поля. Дата, указанная в вакансии (начало работы, срок подачи), сверяется с источником вакансии и календарем до согласия. Перенос слота — новая версия плана и пакета с новым согласием; старые версии сохраняются.

**EMAIL_TO_SEND.txt (R20).** Каждый готовый пакет имеет этот файл в UTF-8, чтобы человек мог отправить заявку вручную, если автоматический путь недоступен. Он строится из утвержденного текста письма и не является вторым источником текста. Структура ниже — документационный пример только с заполнителями:

~~~text
ОТПРАВЛЯЮЩИЙ АККАУНТ: [подтвержденный адрес Gmail]
ПОЛУЧАТЕЛЬ: [адрес из вакансии или официального сайта; источник и дата проверки]
ТЕМА: [утвержденная тема, не более 50 символов]
ВЕРСИЯ ПАКЕТА: [ID заявки, версия пакета, SHA256 manifest]
ПЛАНОВЫЙ СЛОТ: [дата, местное время, часовой пояс]
ВЛОЖЕНИЯ: [точные имена и локальные пути: PDF резюме, PDF письма или согласованный объединенный PDF]
СТАТУС: [подготовлено | требуется сверка | подтвержденный статус]

=== ТЕЛО ПИСЬМА: КОПИРОВАТЬ ТОЛЬКО ЭТОТ БЛОК ===
[утвержденный текст на языке вакансии, включая подпись]
=== КОНЕЦ ТЕЛА ПИСЬМА ===
~~~

Проверочного перевода в этом файле нет. Файл не содержит инструкций внутри тела и утверждения, что письмо отправлено.

## 7. Планирование, Gmail и контроль отправки

### 7.1 Очередь

ИИ-агент ведет очередь как данные внутри папки проекта. Ритм выбирается точно, одним из значений `schedule.cadence` (см. `examples/settings.example.json`): `immediate` (одна отправка в каждый разрешенный день), `allowed_workdays`, `every_second_allowed_workday`, `every_n_calendar_days`, `every_n_allowed_workdays` или `selected_weekdays`. При `approval_per_message` ритм — `on_request`: фиксированного слота нет, время отправки — момент ответа человека на карточку отправки. Календарные дни и разрешенные рабочие дни — разные величины, и пользователь говорит, какая имеется в виду. В плановых ритмах один запуск отправляет не более `max_per_run` писем (1 или 2). Во всех режимах число подач CV за один местный день ограничено `max_per_day` — настройкой профиля, которую выбирает человек: целое число от 1 до 43 (предлагаемое по умолчанию значение для нового профиля — 2; 0 и 44 или больше отклоняются). Месячный лимит 44 остаётся фиксированным и этой настройкой не меняется; изменение `max_per_day` действует с следующего местного дня. При двух — либо используется второе точное местное время (`local_send_times`), либо вторая отправка идет после первой через `inter_message_delay_minutes`. Каждое письмо — отдельная персонализированная операция со своим пакетом. План фиксирует часовой пояс, регион праздников и проверенный календарь, исключенные даты, правило перехода на летнее время (неоднозначное или отсутствующее местное время выносится пользователю либо применяется ранее согласованное правило) и политику пропущенного запуска. Праздники и предпочтения не выдумываются. Календарь точных слотов показывается до принятия плана. Веб-панель очередь не исполняет: агент работает с ней в своем чате или в запланированной задаче, наличие которой он проверил. Сохранять дату создания и изменения плана, статус подготовки и результат. Пользователь поручает агенту обработать очередь в чате либо задает повторный запуск средствами самого агентного приложения, если оно поддерживает расписание проекта. Очередь не исполняется веб-панелью.

Квота JobPilot относится только к заявкам, которыми управляет JobPilot: не более 44 подач с резюме на человека за календарный месяц по всем его профилям JobPilot. Самостоятельные подачи пользователя вне JobPilot — его решение; агент их не ограничивает и не добавляет в квоту JobPilot лишь потому, что нашёл их в Gmail. Ручная отправка утверждённого пакета JobPilot через `EMAIL_TO_SEND.txt` остаётся управляемой подачей и занимает один слот. Ответы и отчёты без CV сохраняют отдельные правила. На системную квоту влияют только неопределённые управляемые попытки; посторонняя личная почта её не меняет.

Управляемые JobPilot повторная подача, замена после недоставки и последующий ответ с CV занимают отдельный слот. Подтверждённая недоставка не возвращает слот реальной отправки; доказанная неотправка может освободить резерв.

Календарный месяц определяется часовым поясом человека. Все его рабочие профили и очереди используют общий журнал квоты; перед отправкой слот резервируется в журнале по правилу единственного писателя, чтобы параллельные чаты не превысили лимит. Сумма фактических отправок и активных резервов никогда не должна превышать 44, а 45-я заявка блокируется еще при планировании. План равномерно распределяет подачи по разрешенным рабочим дням, исключает выходные и выбранные праздники и не создает пакетную рассылку. После исчерпания слотов — жесткая блокировка новых отправок с резюме до следующего календарного месяца; остаток целей остается в ожидании и перед переносом требует повторной проверки актуальности вакансии и пользовательского согласия. В настройках можно снизить лимит, но нельзя поднять выше 44 без изменения версии спецификации самим автором. Самостоятельные внешние подачи не расходуют квоту JobPilot. Если системный счётчик неполный или повреждён, агент приостанавливает только свои отправки до сверки системного остатка.

Проект ограничивает подачи с резюме числом **44 на человека за календарный месяц**, общим для его профилей. Например, можно распределить по две отдельные персонализированные заявки на каждый из 22 рабочих дней; фактическое расписание выбирает пользователь. Ни лимит, ни темп сами по себе не гарантируют, что провайдер не сочтёт письмо спамом. Благодарности и вопросы о сроке без резюме не занимают CV-слот, но требуют отдельного согласия, релевантности и дедупликации. Три вида отправки разделены: `cv_submission` (занимает слот), `thank_you` и `ordinary_reply` (слот не занимают; ответ с резюме является `cv_submission`). Вопрос о сроке — это `ordinary_reply`, который отправляется только после одобрения человеком. У каждого вида свой ключ повтора: подача с резюме — на одну попытку подачи заявки; благодарность — аккаунт + Gmail Message-ID входящего письма; обычный ответ (в том числе вопрос о сроке) — аккаунт + Gmail Message-ID входящего письма, а на одну цепочку — один вопрос о сроке. `thank_you_sent` — единственное автоматическое follow-up. Благодарность допустима после уже отправленного резюме. Неопределенная отправка блокирует все новые отправки для этого человека до разрешения.

Безопасный режим после установки — **только подготовить проект/черновик**. Отправка включается только отдельной настройкой конкретного профиля и подтвержденным OAuth. Режимы должны быть явными: **draft_only**, **approval_per_message**, **scheduled_send_with_profile_consent**. Новый пользователь начинает с draft_only; настройки существующих пользователей независимы и не входят в публичный репозиторий. Согласие связывается с аккаунтом, получателями/каналами, версией пакета и условиями; изменение получателя, текста или вложения после проверки отменяет готовность к отправке.

Перед реальной отправкой сверить профиль и аккаунт Gmail, получателя, тему (для профилей с правилом — максимум 50 символов), тело, файлы, даты, разрешенный канал и согласие. Во время разработки/тестов использовать синтетическую почту и тестовый режим; никогда не посылать тестовые заявки работодателям.

Для первого релиза тема по умолчанию ограничена 50 символами Unicode после нормализации NFC, включая пробелы и знаки препинания. Более строгий лимит пользователя сохраняется. Это настройка продукта, а не заявленный лимит Gmail. Если «через день» не уточнено, использовать каждый второй разрешенный рабочий день; показать календарь до принятия плана. Пропущенную отправку не выполнять задним числом и не нагонять пачкой: отметить как overdue и согласовать новый слот.

Перед планированием или отправкой управляемого CV сравнить нормализованный адрес с последним получателем CV JobPilot и соседними утверждёнными/запланированными слотами JobPilot по профилям этого человека. Удалить краевые пробелы, нормализовать Unicode и сравнивать без учёта регистра; не удалять plus-теги/точки и не приравнивать алиасы без доказательства. Две подряд управляемые CV-подачи на один адрес блокируются с `RECIPIENT_CONSECUTIVE`, даже при разных ID заявок. Дубль отложить и предложить пересмотр плана; не добавлять фиктивную заявку ради обхода проверки. Сохраняются ключи повтора одной заявки и сверка неопределённой отправки. Благодарности и обычные ответы в цепочке имеют собственные ключи и не считаются новыми CV-заявками.

### 7.2 Gmail через встроенный браузер

Gmail можно подключить через официальный одобренный коннектор, доступный в установленном агенте, или через встроенный Browser ChatGPT Desktop/Codex. При настройке проверить реально работающие возможности и дать пользователю выбрать способ. Коннектор использует официальный вход и должен показывать нужный аккаунт и отдельно права чтения/отправки. Для Browser пользователь лично входит в Gmail; агент использует сессию только после проверки видимого адреса и разрешений сайта. Сессия браузера хранится в профиле приложения, не в папке проекта, и может завершиться. Не утверждать, что токен хранится в проекте или доступ бессрочный. Не просить пароль/одноразовый код.

Для Browser включить Computer Use, если он требуется: Desktop → Codex → Plugins → Computer Use; Settings → Browser → Agent permissions. В Windows он управляет видимым окном активного рабочего стола и может занять передний план. Текущую настройку сверять с официальной справкой по [встроенному браузеру](https://help.openai.com/en/articles/20001277-using-the-built-in-browser-in-the-chatgpt-desktop-app) и [Computer Use](https://learn.chatgpt.com/docs/computer-use). Коннектор может иметь другой набор функций; проверять его отдельно.

Перед классификацией прочитать всю цепочку и записать account ID, Gmail message ID, RFC Message-ID при наличии, thread ID, From/To, тему, часовой пояс, связь с пакетом и результат. Поиск и дедупликация не удаляют, не архивируют в Gmail, не перемещают и не меняют метки. Ответ по старой заявке относится к месяцу получения и учитывается один раз на Gmail Message-ID. SENT подтверждает отправку, но не доставку; молчание не доказывает bounce.

Встроенный Browser не умеет автоматически загружать файлы, согласно его официальной документации, проверенной 8 октября 2026 г.; поэтому загрузку выполняет человек либо отдельно одобренный инструмент, загрузка которого фактически проверена. Коннектор может поддерживать вложения, но это нужно проверить для выбранного аккаунта. Постановка через браузер в Gmail Scheduled описана в §7.2a и применима только там, где вложения проверяемы. Письмо с CV не готово только потому, что поля заполнены: проверить список вложений и плановое письмо. Если выбранный способ не прикрепляет документы, остановиться и использовать ручной сценарий: в EMAIL_TO_SEND.txt указаны точные аккаунт, получатель, тема, текст, пути вложений и время; пользователь создаёт письмо, прикрепляет документы и выбирает Gmail «Запланировать отправку». Не заявлять об успешной загрузке или Scheduled без проверки результата.

Не устанавливать и не настраивать случайный сервер/коннектор. Использовать существующий официальный коннектор, явно одобренный для профиля, либо встроенный Browser. Проверить, умеет ли выбранный способ читать полные цепочки, подтверждать SENT, прикреплять файлы и ставить Gmail Scheduled. Не менять метки, не архивировать в Gmail и не удалять письма.

### 7.2a Постановка в Gmail «Запланированные» через встроенный браузер (R03)

Постановка в Gmail — отдельное внешнее действие, не совпадающее ни с отправкой, ни с локальной очередью. Она используется только когда режим подключения это допускает, человек сам вошел в нужный аккаунт и загрузка вложений проверена в этой установке (ограничение см. в §7.2). Иначе применяется ручной путь раздела 6. Каждый шаг проверяется:

1. **До.** Проверить человека, активного отправителя Gmail, режим и согласие, утвержденный слот плана, получателя, тему (не более 50 символов), тело и вложения (SHA256 по manifest).
2. **Резерв.** Если утвержденный план этот слот уже не зарезервировал, записать `quota_reserved` на месяц планируемой отправки; слот не резервируется дважды. Затем записать долговечное намерение (`send_started`, транспорт `gmail_scheduled`) до первого клика, который может что-то сохранить. Строка намерения перечитывается и должна быть последней строкой журнала до первого клика (жесткое условие, ARCHITECTURE.md §6, шаг 3).
3. Открыть новое письмо, заполнить только утвержденные поля, прикрепить только утвержденные файлы и дождаться окончания всех загрузок.
4. Выбрать **Запланировать отправку**, а не «Отправить». Задать точную дату и местное время, проверить часовой пояс.
5. **Проверить в «Запланированных».** Сверить запись с аккаунтом, адресатом, темой, текстом, вложениями, датой и временем. Нажатие кнопки или уведомление доказательством не является.
6. Сохранить удаленный идентификатор или locator доказательства, который дает Gmail. Идентификатор не придумывается.
7. Записать `gmail_scheduled_verified`, обновить проекции и архив. Это не событие отправки.
8. **После планового времени.** Проверить SENT на точное письмо и фактическое время отправки. Записать `sent_verified` один раз и превратить резерв в расход квоты.

Состояния журнала сопоставлены с событиями `DATA_CONTRACT.md` §3c: `local_planned` = `plan_committed`; `scheduling_started` = `send_started` с транспортом `gmail_scheduled`; `schedule_failed_before_commit` = `failed_before_send` с `quota_released` (отсутствие доказано); `schedule_uncertain` = `send_uncertain`; `gmail_scheduled_verified`; `sent_verified`; `schedule_changed` и `schedule_cancelled` — только после подтвержденного удаленного изменения.

**Неизвестный результат.** Если шаг завершился неясно (страница сломалась после клика, сессия истекла, появилась CAPTCHA или защитное подтверждение), искать точную запись в «Запланированных» и в SENT по аккаунту, пакету, адресату и слоту. Второе письмо «на всякий случай» не создается. Если запись не найдена, записать `send_uncertain`: резерв остается, затронутые действия и резервы блокируются, пока человек не решит после проверки. Истекшая сессия, CAPTCHA, защитное подтверждение и ограничения инструмента передаются человеку; ничего не обходится.

**Изменение и отмена.** Только с разрешения человека и только для точно найденной записи. Результат проверить в Gmail до переноса или освобождения резерва. Отмена в Gmail обычно возвращает письмо в черновики и не является разрешением что-либо удалять. Отзыв согласия в локальном файле не отменяет письмо, которое уже хранится в Gmail; об этом человек должен знать до любой удаленной отмены.

**Сроки.** Gmail отправляет запланированное письмо даже тогда, когда агент не работает, и резерв остается активным при закрытом чате. Поэтому согласие, календарь, пакет и резерв проверяются до постановки; агент не может обещать еще одну проверку в момент отправки. Письмо, задержанное через границу месяца, сверяется с реальной датой, а квота учитывается консервативно до подтверждения отправки.

### 7.2b Подготовка месяца и вопрос в начале месяца (R04)

В начале каждого месяца агент один раз, на человека и месяц, спрашивает, готовить ли поиск и пакеты на следующий месяц. Вопрос показывает сохраненные предпочтения, уже отправленные заявки, действующие резервы и подтвержденную квоту. Человек может подтвердить прежние настройки, изменить их или пропустить месяц. Ежемесячное напоминание — реально настроенная задача агента в согласованное при настройке время (`schedule.monthly_reminder_local_time`). Если устройство или агент были недоступны, пропущенный вопрос показывается один раз при следующем запуске. Повторный запуск второго вопроса не создает.

Без ответа новый план не утверждается и новые письма автоматически не ставятся. Уже согласованные письма и уже поставленные в Gmail письма остаются действующими до подтвержденного изменения или отмены.

Весь месяц готовится до какой-либо постановки:
1. Проверить профиль, подтвержденные факты, языки, географию, транспорт, направления и число заявок в пределах общего лимита 44.
2. Проверить существующую базу всех месяцев и профилей того же человека и исключить повторно использованные фирмы и вакансии по утвержденным правилам. Персональные данные между людьми не переносятся.
3. Найти и проверить вакансии или фирмы, контакты, источники и актуальность; при необходимости оценить дорогу; карточки и источники сохранить в месячных папках.
4. Подготовить отдельное резюме, сопроводительное письмо и текст письма под каждую вакансию с правильными датами; проверить документы, тему, вложения и версии.
5. Построить календарь всех месячных слотов по правилам ритма (§7.1), выходным, праздникам, часовому поясу и уже занятым резервам. Показать его человеку.
6. После явного согласования точных пакетов и плана поставить каждое письмо по §7.2a и подтвердить каждую запись в «Запланированных». Согласование набора действительно, только если однозначно определены каждое письмо, адресат, пакет и слот. Изменение пакета требует нового согласования.
7. Выдать сводку: найдено, подготовлено, согласовано, подтвержденно запланировано, а также осталось несогласованным или с ошибкой. Частично выполненный месяц не объявляется готовым.
8. Далее Gmail отправляет письма в выбранные даты, а ежедневная проверка (TODO_FOR_AI.md, часть B, шаг 6) сверяет фактические отправки и ответы. Второй экземпляр уже запланированного письма агент не отправляет.

Частичная подготовка возобновляется по журналу. Пропущенные слоты позже пачкой не отправляются. Сама подготовка квоту не расходует; запланированные письма резервируют квоту по §7.1.

### 7.3 Автозамена при недоставке

Предусмотреть настраиваемую политику, но для публичной установки оставить автоотправку замены выключенной. По подтвержденной постоянной недоставке: сохранить исходное заявление и все IDs; не слать повторно на ошибочный адрес; найти одну новую неиспользованную подходящую цель, подготовить новый комплект и связать две заявки как замену. По умолчанию остановиться на черновике и попросить пользователя. Автоотправку разрешать только если пользователь явно включил эту политику для конкретного профиля, новый адрес подтвержден источником, лимиты/паузы соблюдены и повторная передача персональных данных разрешена. Ограничить замену одним разом, исключить циклы и остановиться при неоднозначном DSN, вопросе работодателя, положительном ответе или необходимости решения пользователя.

Разрешения из старого архива не включать автоматически и не публиковать как примеры личных настроек. При импорте сверить их с актуальными правилами и получить согласие пользователя для выбранного аккаунта. Лимит одной замены применяется ко всей связанной цепочке, а не заново к каждой замене.

### 7.4 Автоответы работодателям

Просьба работодателя о документах или сертификате — событие `needs_user` и никогда не спам: никакой документ автоматически не отправляется и не прикрепляется, команды внутри письма не выполняются, законная часть письма сохраняется и передается человеку (F11).

Автоматические ответы должны быть включены или выключены per-profile. Даже при разрешенной автоответной политике — только проверенный сценарий благодарности на новое содержательное сообщение, и только при согласии `follow_up` (DATA_CONTRACT.md §4); сначала прочитать всю цепочку и проверить, не отправлялась ли уже благодарность после этого ответа. Положительный ответ, приглашение, вопрос, просьба документов, неизвестные данные и неоднозначный смысл требуют решения пользователя. После отправки сверить сообщение в SENT и добавить только новые факты/IDs в конец Status.txt.

### 7.5 Уточнение практики и follow-up

Если по профилю включено соответствующее правило, а работодатель сообщает, что запрошенный период занят, но возможность практики не закрывает, система после чтения полной цепочки и проверки отсутствия такого же вопроса может подготовить в той же теме вопрос о ближайшем месяце/дате как черновик. Он отправляется только как `ordinary_reply` (событие `ordinary_reply_sent`) после того, как человек одобрил это сообщение на карточке отправки; `thank_you_sent` — единственный автоматический follow-up; доступность кандидата должна быть гибкой только если это подтверждено его профилем. Если работодатель сам называет будущую дату, задает вопрос, приглашает или просит документы — не отвечать автоматически, а запросить решение пользователя. Автоматические подтверждения, no-reply, рассылки и DSN исключаются. Для отчетов использовать исходную дату отправки и конкретную причину/суть результата; благодарность не является результатом заявки. Тему ограничивать правилами профиля (например, максимум 50 символов). Итоговый отчет не отправлять по email без отдельного указания.

### 7.6 Порядок внешнего действия и файл блокировки (F07)

Подготовка пакета не является внешним действием. Каждое внешнее действие идет в таком порядке:
1. **Неизменяемый пакет:** проверенная копия с manifest, где перечислены SHA256 каждого вложения (обе части заявки), адресат и его источник, отправляющий аккаунт, тема, тело, транспорт и слот с часовым поясом.
2. **Согласие, привязанное к этому manifest.** Изменение любого перечисленного компонента аннулирует прежнее согласие; изменение — новая версия, которой нужно новое одобрение.
3. **Резерв и долговечное намерение** (`quota_reserved`, если утвержденный план слот уже не зарезервировал, и `send_started`) под файлом блокировки, сохраненные до вызова. Жесткое условие: строка намерения перечитывается и должна быть последней строкой журнала непосредственно перед вызовом; если запись, перечитывание или эта проверка не прошли, вызова нет и ничего другого не записывается (ARCHITECTURE.md §6, шаг 3).
4. **Один внешний вызов.** Повтор в том же чате не допускается.
5. **Сверка** в SENT или «Запланированных». Неизвестный результат — `send_uncertain`, а не повтор.
6. **Факт записывается событием его собственного вида:** для `cv_submission` — `sent_verified` с `quota_consumed` или `failed_before_send` с `quota_released`, когда отсутствие доказано; благодарность и ответ без CV (в том числе вопрос о периоде) имеют свои события, `thank_you_sent` и `ordinary_reply_sent`, но не `sent_verified`; постановка в Gmail имеет `gmail_scheduled_verified`.

Файл `journal/writer.lock` берется эксклюзивным созданием. Проверка «файл отсутствует» с последующим отдельным созданием эксклюзивной не является. Владелец снимает свою блокировку только после прохождения перечитывания последней строки журнала, которую он записал, проверив сначала её `lock_id`; неудачная запись сохраняет блокировку и останавливает чат. Блокировку не снимают только потому, что она старая: сначала проверяют владельца, незавершенные операции и удаленное состояние, затем следуют документированному восстановлению. Резерв не освобождается по таймауту. Если среда не может обеспечить эксклюзивное создание, агент сообщает об этом и не выполняет автономных параллельных действий. Чек-лист — в `TODO_FOR_AI.md`, часть C.

## 8. Ежедневный и месячный отчет

Ежедневный прогон выполняет локальный ИИ-агент по запросу пользователя или по задаче, расписанной в самом агентном приложении, если эта возможность доступна. Агент сверяет выбранный Gmail, текущие отправки, новые содержательные ответы и ошибки; включает ответы текущего месяца на заявки из предыдущих месяцев. Таблица может содержать номер, дату отправки, дату ответа, фирму, адрес, email, канал, краткий ответ, конкретный результат и дату проверки. Месячная сводка дополнительно показывает: фактически использованные слоты из 44, зарезервированные/запланированные слоты и остаток. Если событий нет, явно сообщить, что изменений нет. Запись событий должна быть идемпотентной по Gmail Message-ID. DOCX и PDF создаются инструментом документов установки (сначала инструментом платформы, иначе LibreOffice в режиме без интерфейса). Если ни один не может их выдать, те же числа сохраняются как простой текстовый файл UTF-8, человек извещается, что DOCX и PDF не созданы, и визуальная приемка не заявляется.

Язык документов и языка отчета выбираются независимо в настройках каждого профиля. Пользователь может задать язык CV, сопроводительного письма/текста отправки и отчета отдельно; агент не угадывает язык по стране, вакансии или языку интерфейса. Если обязательный язык не задан, сначала спросить пользователя.

Пользователь может приложить свой шаблон отчета. Агент использует его только как образец оформления и создает отдельную копию результата; исходник не изменяет. В итоговом документе не должно быть названия, логотипа, реквизитов, идентификаторов дела или иных признаков конкретного ведомства/программы. Если шаблон невозможно нейтрализовать, не использовать его молча: сообщить пользователю и предложить нейтральную таблицу либо запросить подходящий шаблон.

Если шаблон не предоставлен, сформировать обычный нейтральный отчет на выбранном языке. В шапке указать фамилию и имя пользователя, период отчета и, при необходимости, направление поиска. Основная таблица включает дату подачи, фирму/адрес, вакансию или специальность, канал подачи, дату ответа и краткий фактический результат. Если ответа нет, писать эквивалент фразы «ответ не получен» на выбранном языке. Если ответ есть, кратко указывать его суть или причину отказа; благодарность работодателю не является результатом заявки. Не добавлять институциональные поля, номера дел, ведомственные колонки или фирменные формы.

В последний согласованный рабочий день месяца:

1. собрать подтвержденные подачи месяца и новые ответы месяца на старые заявки;
2. исключить повтор ответа по Message-ID и дубли заявки;
3. показывать фактическую исходную дату подачи и фактическую дату ответа;
4. визуально проверить все страницы редактируемого DOCX и PDF, исходный пользовательский шаблон не изменять;
5. добавить отдельную страницу PDF с датой исследования, выбранными профессией/радиусом/транспортом, источниками и охватом, оценкой вакансий и работодателей, уже использованными и еще не проверенными вариантами и рекомендацией. Рыночная страница — часть основного сценария, а не молча отключенная опция. Если источники недоступны, прямо написать «оценка недоступна» и причину, не придумывать числа.

Страница/раздел анализа рынка показывает дату исследования, заданные профессию/радиус/транспорт, источники и охват, примерное число актуальных вакансий, уникальных релевантных работодателей, уже использованных, еще не проверенных/не использованных и осторожную рекомендацию по расширению поиска. Каждое число — оценка с источниками и датой, не обещание полного реестра и не гарантия наличия всех вакансий. Не смешивать подтвержденную статистику с предположениями. Тема письма с отчетом, если пользователь отдельно поручил его отправить, должна соответствовать лимиту профиля; сам файл хранится локально и не отправляется автоматически.

Отчет сохраняет manifest с периодом, cutoff, revision, ID включенных заявок и ответов. Повторная генерация того же месяца — новая ревизия, а не повторный учет событий. Ответ после cutoff, но до конца того же месяца, остается в этом месяце и при необходимости создает дополнение/ревизию; в следующий месяц он не переносится. Состояние «ответ не получен» означает отсутствие содержательного ответа на cutoff. При отказе без причины писать «отказ, причина не указана», а не угадывать мотив. Различие числа ответных сообщений и числа заявок с ответом определено в DATA_CONTRACT.md.

### 10.1 Порядок установки: агент, затем архив, затем подключение

Пошаговая инструкция для пользователя существует в двух видах с одним содержанием: `USER_GUIDE.md` и HTML-страница `overview_install.html` (русская редакция — `docs/ru/overview_install.html`). Оба вида обязательны в каждом релизе; при изменении одного обновляется другой. Для владельца проекта типична чистая Windows без Git и инструментов разработки, поэтому инструкция не требует ставить Git, Python или Node, архив скачивается кнопкой **Code → Download ZIP** в браузере, каждый шаг содержит одно действие, описание того, что должно появиться на экране, и подсказку на случай ошибки.

Установка делится на три части в строго таком порядке:

1. **Агент.** Установить ChatGPT Desktop с официальной страницы, войти, выбрать Codex и убедиться, что он доступен. По данным OpenAI на 09.10.2026, Codex включён в планы ChatGPT, включая Free и Go, но лимиты зависят от тарифа; Plus рекомендуется для регулярного использования и указан по цене 20 долларов в месяц в США. Условия меняются: перед покупкой проверить актуальные [условия доступа Codex](https://help.openai.com/en/articles/11369540-using-codex-with-your-chatgpt-plan) и [цену Plus](https://help.openai.com/en/articles/6950777-what-is-chatgpt-free-plan). Агент настраивается первым, поскольку доступность и лимиты зависят от аккаунта и организации.
2. **Папка проекта.** Скачать ZIP из опубликованного репозитория и распаковать его в отдельную папку; проверить, что `README.md`, `USER_GUIDE.md`, `AI_BUILD_SPEC.md`, `AGENTS.md`, `CLAUDE.md`, `TODO_FOR_AI.md`, `dashboard_template` и папка `Локальные_данные\Положите_сюда` с тремя подпапками лежат прямо в ней, а не во вложенной папке. Архив — просто набор файлов; польза появляется, когда агент его открывает.
3. **Соединение и первый запуск.** Создать локальный проект или открыть папку и назначить распакованный корень основной папкой (primary); создать чат внутри проекта в локальной среде (Local); включить `Ask for approval`; выполнить стартовый запрос в режиме draft-only.

После этого пользователь кладёт материалы в три папки `Положите_сюда` (это можно сделать даже до шага 1) либо позволяет агенту провести интервью и подтверждает факты базы знаний (до первого чтения чего-либо облачным агентом он даёт согласие на передачу выбранных сведений), отдельно подключает Gmail, готовит и проверяет первую очередь, при необходимости включает Computer Use, переходит к ежедневной работе и расписанию, открывает статистику и отчеты, делает резервную копию и обновляет пакет.

Руководство различает локальный проект с папкой компьютера и обычный облачный ChatGPT Project: имя чата или путь, написанный в сообщении, не дает файловый доступ. Если релиз еще не опубликован, URL GitHub, кнопки и структура пакета не выдумываются: ссылка помечается как ожидающая выпуска. Codex и Claude Code — альтернативные агенты; разрешения и почтовые подключения в них настраиваются отдельно. Официальные ссылки и пункты интерфейса проверяются перед каждым релизом.

Агент, который ведет пользователя по установке, называет номер шага, действие и ожидаемый результат, не переходит к следующему шагу, пока пользователь не подтвердил результат предыдущего, и не предлагает ставить инструменты разработки на компьютер пользователя. Файлы `AGENTS.md` и `CLAUDE.md` содержат тот же порядок шагов.

### 10.3 Подключение Gmail через коннектор или встроенный браузер

1. Попросить агента перечислить почтовые способы, доступные в текущем Codex. Пользователь выбирает существующий официальный одобренный коннектор или Browser; произвольный сервер не добавлять.
2. Для коннектора пользователь входит через официальный экран. Для Browser написать: «Открой Gmail по адресу https://mail.google.com во встроенном браузере. Пока ничего не читай и не отправляй — я сначала войду сам». Пользователь выбирает аккаунт и проходит подтверждения Google.
3. Проверить точный адрес Gmail. В профиль записать только несекретный account ID. Для коннектора отдельно проверить права чтения и отправки; для Browser — разрешения сайта в Settings → Browser → Agent permissions.
4. Если Browser требует Computer Use, включить его в Codex → Plugins → Computer Use и разрешить только нужный браузер. Сверять актуальные названия меню и не разрешать все приложения.
5. Начать только с чтения цепочек. Отправка и планирование требуют отдельного согласия.
6. Проверить поддержку вложений и Scheduled выбранным способом. Если файлы не загружаются автоматически, пользователь прикрепляет их сам и проверяет список перед планированием.

Если ни одобренный коннектор, ни Browser/Computer Use недоступны, использовать EMAIL_TO_SEND.txt для ручного копирования в браузере пользователя. Не настраивать случайный MCP/OAuth-сервер и не хранить токены, cookies, пароли или одноразовые коды в проекте. Доступ к чтению Gmail не является разрешением отправлять или планировать. Страница статистики не имеет Gmail-доступа.

### 10.4 Повторные проверки и расписание

В начале месяца агент один раз спрашивает, готовить ли поиск, пакеты и план отправок на этот месяц. Пользователь утверждает точные адресаты, manifest пакетов, местное время и cadence до работы с Gmail. По умолчанию ежедневная проверка почты назначается на 16:00 в часовом поясе пользователя. Если в установленном ChatGPT Desktop/Codex доступны Scheduled tasks для локального проекта, пользователь может попросить создать повторяющуюся задачу. Проверить, что она появилась в Scheduled, и просмотреть первый результат. Для локальной папки компьютер и приложение ChatGPT должны оставаться доступными.

GUI-сценарий Computer Use в Windows требует видимого окна на активном рабочем столе и может занимать передний план. Не обещать автономную проверку Gmail, если сессия или инструмент не работают. Уже запланированное в Gmail письмо может отправиться независимо от агента. Если Scheduled tasks недоступны или ограничены политикой, пользователь запускает проверку вручную. Актуальные функции и ограничения описаны в [официальной справке Scheduled tasks](https://learn.chatgpt.com/docs/automations).

### 10.5 Обязательная статическая страница статистики

Пакет содержит готовый шаблон `dashboard_template/index.html` и рядом с ним файл данных `summary.js`, заполненный синтетическими примерами (помечены как demo, компании вымышлены), чтобы страницу можно было открыть двойным щелчком и посмотреть. Для реального профиля агент копирует файл страницы **без изменений** и пишет только `summary.js` (`window.JP_DATA = {…}`, после знака равенства — корректный JSON) со снимком одного профиля и `demo: false`; разметку, стили и скрипт никогда не правят. Это сделано намеренно: агенту не нужно редактировать HTML, поэтому ошибка в данных не может сломать страницу. Локальное меню `Локальные_данные/dashboard/index.html` ведёт к страницам `dashboard/profiles/<profile_id>/index.html`. Страница открывается напрямую как файл, без backend, сервера, Docker и внешних JavaScript-библиотек; если `summary.js` нет или он повреждён, страница сообщает об этом, а не показывает неверные числа. Агент считает один раз и копирует одни и те же строки и счётчики в HTML и DOCX/PDF, с одним `source_revision`. Агент проверяет `snapshot_id` и время обновления. Уже открытая старая страница может показать время последнего обновления и предупреждение по возрасту; сама она не узнает, что проверка почты не состоялась.

**Структура.** Страница показывает **год → месяц → день**. У года и месяца есть сводка: отправлено, ответов, заявок с ответом, успешно, неуспешно, ожидание, ошибки доставки, ответы на заявки прошлых месяцев, квота «использовано / зарезервировано / осталось из 44». У каждого дня есть таблица событий: время, событие (отправлено, ответ, не доставлено), компания и город, должность, канал, результат и заметка. Месяцы и дни, где нет событий, не показываются; пустой результат фильтра объясняется текстом.

**Результат записи** принимает одно из значений: «успешно» (положительный ответ), «неуспешно» (отказ), «ожидание» (содержательного ответа нет), «нужно решение пользователя» (приглашение, вопрос, просьба о документах) и «ошибка доставки» (подтвержденная постоянная недоставка; это не отказ работодателя).

**Сортировка:** по дате (сначала новые или сначала старые) и по результату (сначала успешные или сначала неуспешные). По дате упорядочиваются годы, месяцы, дни и строки; при сортировке по результату строки внутри дня идут по результату, а дни остаются по убыванию даты. **Фильтры:** год, месяц, результат, поиск по компании, городу и должности. Есть кнопки «развернуть всё», «свернуть всё» и «сбросить».

**Остальное.** Ответы группируются по месяцу фактического получения, в том числе ответы на заявки прошлых месяцев; в строке ответа показана дата исходной отправки. Даты хранятся в ISO 8601 UTC с часовым поясом снимка; на экране они показываются в этом часовом поясе в понятном формате, а сортировка идет по настоящим меткам времени, а не по строкам `DD.MM.YYYY`. Язык интерфейса — `en` по умолчанию и `ru` (параметр `?lang=ru` или переключатель); словари имеют одинаковые ключи, данные не меняются. Есть светлая и тёмная тема и кнопка «Top» в правом нижнем углу.

Страница только отображает. Она фильтрует и сортирует данные в памяти браузера, ничего не сохраняет (кроме необязательного выбора темы) и не создаёт и не изменяет фирмы, вакансии, заявки, очередь и статусы. Тела писем, CV, Anschreiben, адреса проживания, токены и другие лишние для статистики персональные данные в `summary.js` не записываются. Рабочий `summary.js` и копии страницы находятся в локальном каталоге данных и исключены из Git; чистый шаблон с примерами данных входит в публичный пакет. Открытие, фильтрация и сортировка не подключают Gmail и не меняют источник данных.

## 11. Безопасные критерии готовности

- Невозможно случайно открыть документ или почту другого профиля; это подтверждено негативными тестами.
- Источник, дата проверки, статус подтверждения и версия связаны с каждым существенным фактом.
- Проверяется дубликат работодателя и филиал; не создается повторная заявка без причины.
- Даты и текст из пакета совпадают; DOCX/PDF рендерятся, без обрезки и ошибочных шрифтов.
- Импорт исходных архивов сначала read-only и предоставляет отчет сопоставления/ошибок.
- Gmail не меняет метки/архив/удаление; дедупликация проверяется повторным запуском.
- Статическая `Локальные_данные/dashboard/index.html` открывается двойным щелчком без сервера и сети; сортировка по годам/датам, месячные группы, stale-data marker и отсутствие записи/сетевых запросов проверяются.
- Ни один реальный email не отправляется в тестах; отправка требует утвержденного режима профиля, точного получателя и вложений.
- Автоответ на отказ и авто-подготовка замены не срабатывают на автоматические, временные или неоднозначные сообщения.
- Все события и результаты отчетов можно связать с исходными Gmail Message-ID и источниками вакансий.
- Лимит 44 фактических подач с резюме на человека за календарный месяц не обходится через второй профиль/чат, новый адрес, замену после bounce или иной канал; 45-я отправка блокируется, а очередь не создает рассылку пачкой. Проверить общую квоту при параллельных задачах и безопасный стоп при недоступном журнале.
- Резервная копия восстанавливается; GitHub репозиторий сканируется на личные данные и секреты.

Для каждого критерия выполнить соответствующие сценарии ACCEPTANCE_TESTS.md и сохранить evidence. Пока сценарий не выполнен вручную, его статус — NOT RUN; проверка ссылок в документации не означает готовность почты или защитного механизма.
