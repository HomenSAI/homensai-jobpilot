## 1. Основне рішення: правила і файли

Система — це **ШІ-агент** (Codex або Claude Code), **письмові правила**, **папка з даними** і локальний перегляд статистики. Агент шукає інформацію, пише документи, розмовляє з людиною і зберігає кожен запис як читабельний файл (JSON, JSONL, Markdown, документи). HTML-сторінка не віддає жодних команд; її дані змінюються лише тоді, коли працює агент.

Запобіжники (ліміт 44, ніколи не надсилати двічі, один записувач, нічого не надсилати без дозволу) — це *процедури, яких дотримується агент*, а не технічні блокування. Тому кожне правило — це перелік перевірок перед дією; типовий режим — лише чернетки; автоматичне надсилання потребує письмового визнання людини, що ліміт і захист від дублікатів тоді залежать від агента; а сценарії приймання (ACCEPTANCE_TESTS.md) перевіряють вручну на синтетичних даних до будь-якого реального надсилання.

## 2. Частини і відповідальність

| Частина | Що робить агент | Де зберігається |
|---|---|---|
| Робоча папка, можливості | Папка, формат, людина, профіль; перевіряє кожен інструмент (розділ 7) | `workspace.json` |
| Профіль і база знань | Матеріали та інтерв'ю → запропоновані → підтверджені факти з джерелами; профіль пошуку | `Life_Story.md`, `profile.json` |
| Пошук, планування | Цілі (дублікати, актуальність, радіус, маршрути); слоти, резервування, перенесення | `registry.json`, журнал |
| Документи | Пакети з вимог і підтверджених фактів, версії, візуальна перевірка | папка заявки |
| Пошта | Цілі ланцюжки листування, доказ надсилання, повідомлення, відповіді | журнал, `Status.txt` |
| Звітність | Підрахунки на фіксованій позиції журналу; DOCX/PDF/HTML з однаковими числами | `reports/`, `dashboard/` |

Зміни стану спочатку записуються в журнал. Який файл агент читає і коли: `AGENTS.md`.

## 3. Одиниця обліку — людина

`person_id` об'єднує напрями пошуку однієї людини. Кожен напрям має власний `profile_id`, мови документів, обліковий запис, документи і згоди. Квота і перевірки повторних заявок спільні для `person_id`; різні люди мають окремі журнали.

```text
Local_Data/
  workspace.json  # workspace_id, format, language, stage of the first run, capabilities
  Put_Here/  # the ONLY place where the person puts things; the agent only reads it
    1_My_Documents/  # CVs, diplomas, certificates, references (originals)
    2_My_Story/  # the person's story: transcripts, notes, interviews, the questions
    3_Report_Template/  # optional report template
    4_CV_Templates/  # everything about the CVs, any format; read only
    5_Cover_Letter_Templates/  # everything about the cover letters; read only
  persons/<person_id>/
    Knowledge_Base/Life_Story.md  # the knowledge base: confirmed facts of the life story
    journal/transactions-YYYY-MM.jsonl  # the only authoritative journal; monthly segments, -pN parts above 500 lines
    journal/writer.lock  # exists only while one chat is writing
    state/person.json  # person, profile list, setup_progress
    state/quota.json  # monthly counters, rebuilt from the journal
    outbox/<send_attempt_id>/  # prepared send package, never edited
    runs/  # person-level session notes (first setup)
    archives/  # local archives (DATA_CONTRACT.md §11)
  Resume/  # CV drafts and the Word copy of the template in use; one subfolder per person_id with several people
  CoverLetter/  # the same for cover letters
  profiles/<profile_id>/
    profile.json  # current confirmed configuration
    registry.json  # targets, applications, queue (projection)
    runs/  # session notes: plans, results, questions
    reports/<YYYY-MM>/  # report revisions and manifests
  Applications/<YYYY>/<MM_Month>/  # one tree for all years, e.g. 2026/10_October/
    001_Muster-Maschinenbau_Stuttgart_Maintenance-technician/  # number, company, city, role
      Company.md · Resume_v001.docx/.pdf · CoverLetter_v001.docx/.pdf · EmailText_de.txt · EMAIL_TO_SEND.txt
      Status.txt  # append-only history of this application
      Replies.txt  # every reply and delivery notice in full
  dashboard/
    index.html  # local menu: statistics and readiness per profile
    profiles/<profile_id>/summary.js · index.html · readiness.html  # data; unchanged template copy; readiness page
  Archive/<YYYY-MM-DD>_daily/  # daily full archive of Local_Data, for a USB stick (DATA_CONTRACT.md §11.9)
```

`Local_Data` — технічний шлях у кожній мовній редакції; панель має один шлях, `Local_Data/dashboard/`; ідентифікатори профілів унікальні. Кожен рядок журналу містить `person_id` і, де це стосується, свій профіль; перш ніж діяти, агент перевіряє, що профіль належить цій людині і цьому обліковому запису.

**Ізоляція між людьми і профілями (процедура, F12).** Кожна людина має `persons/<person_id>/` і оригінали в `Put_Here/<name>/`; агент ніколи не відкриває оригіналів, бази знань, журналу, стану, outbox, архівів чи пошти іншої людини. Нова людина проходить TODO_FOR_AI.md, частину A, починаючи з A2 (A1, перевірку робочої папки, не повторюють); її прогрес — це `setup_progress` у `persons/<person_id>/state/person.json` з тими самими назвами етапів, а `stage` у `workspace.json` описує лише налаштування робочої папки першою людиною. Згоди, квота, облікові записи і подання для кожної людини: DATA_CONTRACT.md §17. Це процедурна ізоляція, а не межа операційної системи.

## 4. Один рядок на завершену дію

Журнал — це набір помісячних текстових файлів (правило 8) з одним об'єктом JSON у рядку. Рядок записують, коли дію **завершено**: `schema_version`, `sequence` (1, 2, 3 … без пропусків), `action_id`, `person_id`, `recorded_at`; список `events`, кожна подія з власним унікальним `event_id`; і короткий текст `result`, якого досить, щоб повторити відповідь, якщо ту саму дію запитають знову.

Правила для агента:

1. **Лише дописування.** Старий рядок ніколи не редагують і не видаляють; виправлення — це новий рядок, який називає подію, що його замінює (`supersedes_event_id`).
2. **Перед записом:** прочитайте останній рядок, візьміть наступний `sequence` і перевірте, що цього `action_id` немає в жодному сегменті. Якщо він є, повідомте попередній результат і більше нічого не робіть.
3. **Записуйте весь рядок одразу**, потім оновіть подання (реєстр, черга, `Status.txt`, `quota.json`, статистика). Якщо чат зупиниться посередині, наступний чат їх перебудує (6b).
4. **Пошкоджений або напівзаписаний останній рядок** ніколи не виправляють мовчки: зупиніться, збережіть файл, повідомте людину, відновлюйте з останнього повного рядка і поштових доказів.
5. **Один записувач за раз** (4b). Чуже блокування означає: зупинитися і запитати. Блокування захищає лише тоді, коли кожен чат дотримується протоколу і ексклюзивне створення працює; інакше одночасно працює лише один чат.
6. Рішення щодо квоти чи надсилання завжди перечитує журнал; підсумку з попередньої частини чату ніколи не довіряють.
7. **Рахуйте власним засобом системи, а не на око.** Використані, зарезервовані і неперевірені слоти місяця рахують текстовим пошуком полів місяця в подіях квоти в усіх сегментах (формули: DATA_CONTRACT.md §3c, вільна кількість: DATA_CONTRACT.md §5; команди: §4a). Агент показує число і як його знайдено та порівнює з `quota.json`; у разі розбіжності чи відсутнього файлу правий журнал, а `quota.json` перебудовують (`examples/quota.example.json`).
8. **Запис рядка (один спосіб дописування, помісячні сегменти).** Поточний сегмент — це `journal/transactions-YYYY-MM.jsonl` місцевого місяця людини або його частина `journal/transactions-YYYY-MM-pN.jsonl`, щойно в місяці набереться 500 рядків (DATA_CONTRACT.md §3c); закритий сегмент ніколи не редагують. Сегменти, файл блокування і файли JSON — UTF-8 без BOM, лише з закінченнями рядків LF, і закінчуються рівно одним LF. JSON не складають вручну; текст не записують перенаправленням у shell чи heredoc; точну заміну файловим інструментом використовують лише для кроку 3.
   1. **До.** Під блокуванням запису знайдіть поточний сегмент (на 500 рядках наступна частина `-p2`, `-p3` … — це новий сегмент). Прочитайте його останній рядок, який має бути повним; якщо сегмент новий або порожній, прочитайте останній рядок найновішого попереднього сегмента (для найпершого рядка `n` дорівнює 0). Візьміть `n`, його `sequence`; перевірте, що нового `action_id` немає в жодному сегменті. Запишіть у нотатку запуску: кількість рядків; останній рядок `L` без розриву рядка (унікальний: він містить свої `sequence` і `action_id`); `S0`, розмір сегмента в байтах; і `C0`, SHA-256 усього сегмента (новий сегмент: `S0` 0, `C0` — SHA-256 порожнього файлу, `e3b0c442…b855`). Перевірте, що файл закінчується на LF, не має CR і не має BOM.
   2. **Побудова** нового рядка `N` у порядку ключів з DATA_CONTRACT.md §3c з `sequence` n+1: один об'єкт JSON в одному рядку, ідентифікатори — як у DATA_CONTRACT.md §2. Невдала перевірка зупиняє роботу (крок 5).
   3. **Дописування.** (a) Сегмент із рядками: замініть `L` на `L`, розрив рядка і `N` точною заміною файлового інструмента (для дуже довгого `L` досить унікального кінця). Якщо `L` знайдено не рівно один раз, зупиніться. (b) Новий сегмент: перевірте, що файлу немає, потім створіть його файловим інструментом, щоб він містив рівно `N` і його розрив рядка. (c) Сегмент, коротший за 300 рядків, можна натомість записати цілком файловим інструментом: рядки, прочитані на кроці 1, потім `N` і його розрив рядка; це єдине переписування цілого сегмента.
   4. **Перечитування.** (a) `N` розбирається з `sequence` n+1; рядок перед ним, якщо є, побайтово ідентичний `L`. (b) Кількість рядків зросла рівно на один. (c) SHA-256 перших `S0` байтів дорівнює `C0` (жоден попередній байт не змінився), а новий розмір — це `S0` + байти `N` + 1. (d) Наприкінці досі LF, немає CR, немає BOM. Запишіть значення в нотатку запуску.
   5. **Невдача.** Будь-яка невдала перевірка зупиняє запис: збережіть сегмент, не оновлюйте жодного подання, не виконуйте жодної зовнішньої дії, зберігайте блокування, повідомте людину (правило 4). Попередні рядки ніколи не переписують як виправлення.
   6. **Звільнення.** Лише після того, як крок 4 пройдено: прочитайте блокування, перевірте `lock_id` цього чату, видаліть його (4b).

### 4a. Команди, які може використовувати агент

Лише команди, які вже є в системі, набрані безпосередньо; жоден скрипт не зберігається, а Python — лише засіб аудиту тестувальника. Крім таблиці: перелік і створення папок, `cmp` або `diff` лише для читання (наприклад, щоб перевірити, що історію збережено дослівно), і власні тимчасові файли агента. Файли JSON і текстові файли (Status.txt, Company.md, нотатки запусків, EMAIL_TO_SEND.txt) записують файловим інструментом, ніколи перенаправленням у shell, heredoc, `sed` чи подібним; рядок журналу — лише за правилом 8. Винятки: створення `writer.lock`, копіювання в `outbox/`, засіб роботи з документами і одноразовий поділ старого журналу (DATA_CONTRACT.md §3d), який копіює байти за діапазонами рядків і перечитується за контрольною сумою.

| Потреба | Linux / macOS | Windows PowerShell |
|---|---|---|
| Час UTC | `date -u +%Y-%m-%dT%H:%M:%SZ` | `(Get-Date).ToUniversalTime().ToString("yyyy-MM-ddTHH:mm:ssZ")` |
| UUID | Linux `cat /proc/sys/kernel/random/uuid`; macOS `uuidgen \| tr 'A-Z' 'a-z'` | `[guid]::NewGuid().ToString()` |
| Поточний місцевий місяць | `TZ=Europe/Berlin date +%Y-%m` (зона IANA людини) | `[TimeZoneInfo]::ConvertTime([DateTimeOffset]::UtcNow,[TimeZoneInfo]::FindSystemTimeZoneById('W. Europe Standard Time')).ToString('yyyy-MM')` (зона IANA, перетворена на назву Windows) |
| Контрольна сума (`C0`) | Linux `sha256sum '<file>'`; macOS `shasum -a 256 '<file>'` | `(Get-FileHash -Algorithm SHA256 -LiteralPath '<file>').Hash.ToLower()` |
| Розмір у байтах (`S0`) | `wc -c < '<segment>'` | `(Get-Item -LiteralPath '<abs path>').Length` |
| Контрольна сума перших `S0` байтів (правило 8, 4c) | Linux `head -c <S0> '<segment>' \| sha256sum`; macOS `head -c <S0> '<segment>' \| shasum -a 256` | `$b=[IO.File]::ReadAllBytes('<abs path>'); -join ([Security.Cryptography.SHA256]::Create().ComputeHash($b,0,<S0>) \| ForEach-Object { $_.ToString('x2') })` |
| Байти останнього рядка з його LF (4c) | `tail -n 1 '<segment>' \| wc -c` | `[Text.Encoding]::UTF8.GetByteCount((Get-Content -Encoding UTF8 -LiteralPath '<abs path>' -Tail 1)) + 1` |
| Закінчується на LF, немає CR, немає BOM | `tail -c 1 '<segment>' \| od -An -c` показує `\n`; `tr -cd '\r' < '<segment>' \| wc -c` дорівнює 0; `head -c 3 '<segment>' \| od -An -tx1` не є `ef bb bf` | з `$b`, як вище: `$b[-1] -eq 10; @($b -eq 13).Count -eq 0; -not ($b[0] -eq 0xEF -and $b[1] -eq 0xBB -and $b[2] -eq 0xBF)` |
| Останні рядки, кількість рядків | `tail -n 1 '<segment>'`, `tail -n 2 '<segment>'`; `wc -l < '<segment>'` | `Get-Content -Encoding UTF8 -LiteralPath '<segment>' -Tail 1` (або `-Tail 2`); `(Get-Content -Encoding UTF8 -LiteralPath '<segment>').Count` |
| Кількість збігів для місяця (правило 7) | `grep -oE '"consumed_month" *: *"2026-10"' <journal> \| wc -l` (ніколи `grep -c`: він рахує рядки, а не збіги) | `(Select-String -Encoding UTF8 -Path <journal> -Pattern '"consumed_month"\s*:\s*"2026-10"' -AllMatches \| ForEach-Object { $_.Matches.Count } \| Measure-Object -Sum).Sum` (порожньо означає 0) |
| Кожен рядок — коректний JSON | Перечитування файловим інструментом: один об'єкт у рядку; `jq empty '<segment>'` лише якщо jq встановлено | `Get-Content -Encoding UTF8 -LiteralPath '<segment>' \| ForEach-Object { $_ \| ConvertFrom-Json } \| Out-Null` |
| Створити `writer.lock` з його вмістом, з помилкою, якщо він існує | `set -C; printf '%s\n' '<lock json>' > '<absolute path>/journal/writer.lock'` (bash або zsh) | `` $f=[IO.File]::Open('<absolute path>','CreateNew','Write','None'); $w=New-Object IO.StreamWriter($f,(New-Object Text.UTF8Encoding($false))); $w.Write('<lock json>'+"`n"); $w.Close() `` |
| Копіювати в `outbox/<send_attempt_id>/` | `cp '<source>' '<outbox folder>/'`, потім контрольна сума кожної копії | `Copy-Item -LiteralPath '<source>' -Destination '<outbox folder>'`, потім контрольна сума кожної копії |
| DOCX → PDF | Спочатку засіб роботи з документами платформи; інакше `soffice --headless --convert-to pdf --outdir '<folder>' '<file.docx>'` | те саме |

`<journal>` — це кожен сегмент `journal/transactions-*.jsonl` людини; `<segment>` — поточний. Шляхи абсолютні і в лапках. Стан shell не зберігається між командами, тож `set -C` і створення блокування — одна команда; JSON блокування не містить апострофа. Форми для Linux випробувано з bash і GNU coreutils; форми для macOS — їхні відповідники BSD. Форми для PowerShell ще не випробувано на справжньому комп'ютері з Windows; перше випробування — частина перевірок приймання.

### 4b. Протокол блокування запису (F07)

**Сфера дії.** Одне блокування на людину, `persons/<person_id>/journal/writer.lock`, для журналу, квоти і подій профілю цієї людини. Воно охоплює лише кроки запису; пошук, відтворення документів і зовнішні виклики відбуваються поза ним. Блокування іншої людини ні блокує, ні дозволяє записи цієї людини.

**Взяття блокування.**

1. Створіть файл **разом із його вмістом однією командою**, яка завершується помилкою, якщо файл існує, з абсолютним шляхом (§4a). Перевірити, що файлу немає, а потім створити його — це не ексклюзивне створення.
2. Вміст — один рядок JSON з `lock_id`, `run_id`, `owner`, `person_id` і `created_at` (DATA_CONTRACT.md §3c, «Файл блокування» [The lock file]); `run_id` також є в нотатці сеансу чату.
3. Якщо файл існує, нічого не записуйте і прочитайте його. Його `run_id` належить цьому чату: продовжуйте (перезапущений чат знає своє блокування з нотатки). Інакше: зупиніться, повідомте `LOCK_HELD`, запитайте людину. **Порожнє або нечитабельне блокування** (власник зупинився між створенням і записом) — це чуже блокування: застосовується процедура застарілого блокування.
4. Перед кожним записом знову прочитайте блокування і підтвердьте `lock_id`; якщо його немає або воно змінилося, відмовтеся від запису і повідомте про це.
5. `capabilities.writer_lock` у `workspace.json` фіксує, чи працює ексклюзивне створення (`available`, `unavailable`, `unknown`). Папки, що синхронізуються з хмарою (OneDrive, iCloud, Dropbox), не дають ексклюзивного створення між пристроями: `unavailable`. Якщо не `available`, агент не заявляє про ексклюзивність, не виконує автономних паралельних записів чи зовнішніх дій і каже людині, що працювати може лише один чат.

**Звільнення блокування.** Лише власник, лише після того, як його останній рядок пройшов перечитування за правилом 8, крок 4 (чат, який нічого не записав, звільняє після своєї останньої перевірки): прочитайте блокування, підтвердьте власний `lock_id`, видаліть його окремим кроком. Невдалий запис залишає блокування і зупиняє чат; блокування ніколи не видаляють тією самою командою, що й запис, який міг не вдатися. Ніколи за віком, іншим чатом чи за тайм-аутом; без рядка журналу.

**Застаріле блокування.** Блокування ніколи не втрачає чинності через вік, а його видалення ніколи не звільняє резервування. Блокування, яке не належить цьому чату, видаляють лише після такого, у такому порядку: (a) людина підтверджує, що чат-власник більше не працює; (b) останній рядок журналу — повний JSON, а `sequence` не має пропусків (DATA_CONTRACT.md §3c); (c) кожну відкриту спробу (`send_started` або намір планування без результату) перелічено, і вона стає `send_uncertain`, якщо її не звірено з SENT чи Scheduled, а папки outbox без результату перелічено; (d) віддалений стан перевірено там, де це дозволяє поштовий інструмент; те, що не можна перевірити, залишається відкритим; (e) блокування видалено, це зазначено в записі запуску і в `result` наступного рядка журналу (не окрема подія). Доки існує відкрита спроба, жодне нове надсилання чи планування для цієї людини не дозволене в жодному чаті.

**Точки збою.** Жодна з них не робить другого зовнішнього виклику.

| Точка збою | Що залишається | Відновлення |
|---|---|---|
| До створення блокування | Нічого | Почати знову |
| Блокування створено (зокрема порожнє), рядок не записано | Лише блокування | Перевірка застарілого блокування; зовнішнього виклику не було; видалити після (a) |
| Під час запису рядка | Можливо, обрізаний останній рядок | Зупинитися, зберегти файл (правило 4); діагностувати з останнього повного рядка |
| Після рядка наміру (`quota_reserved`, `send_started`): до виклику, відповідь втрачено або до рядка результату | Відкрита спроба; виклик міг відбутися | Один раз звірити SENT і Scheduled: перевірено → `sent_verified` + `quota_consumed` (або запис про планування); доведено відсутність → `failed_before_send` + `quota_released`; інакше `send_uncertain`, резервування зберігається, вирішує людина. Ніколи не викликати знову |
| Після рядка результату, до подань | Подання застарілі | Повторне відтворення (6b); жодної зовнішньої дії |
| Два чати змагаються за останній слот | Одне ексклюзивне створення вдається | Той, хто програв, нічого не записує, `LOCK_HELD`; перевірка квоти виконується після взяття блокування |
| Блокування видалив інший учасник під час запису | Запис може зупинитися посередині | Крок 4 зупиняє запис; наступний чат виконує процедуру застарілого блокування |

Без ексклюзивного створення ці правила все одно діють, а паралельні чати для однієї людини взагалі не підтримуються.

Кожна відповідь називає результат (`ok`, `needs_input`, `conflict`, `blocked` або `failed`), код причини, позицію журналу, файли і наступний крок. Коди причин і те, які дії записують рядок: DATA_CONTRACT.md §3c (наприклад, `ACCOUNT_MISMATCH`, `QUOTA_EXHAUSTED`, `SEND_UNCERTAIN`, `PACKAGE_CHANGED`, `SUBJECT_TOO_LONG`, `MODE_DRAFT_ONLY`, `LOCK_HELD`). Пройдена перевірка надсилання — не постійний дозвіл: Надсилання знову перевіряє позицію журналу, час, згоду і пакет.

## 6. Надсилання і outbox

Outbox `outbox/<send_attempt_id>/` містить для однієї спроби копії файлів для вкладення, `message.txt` (отримувач, тема й основний текст точно такі, як надіслано) і `attempt.json` (`account_id`, `application_id`, `send_attempt_id`, `consent_id`, контрольні суми копій); жодних секретів. Спроба з `send_started` і без результату є відкритою.

Кожна зовнішня поштова дія (надсилання, планування в Gmail, перенесення, скасування) виконується за TODO_FOR_AI.md, частина C, «Порядок зовнішніх дій (F07)» [External action order]: незмінний пакет → згода, прив'язана до маніфесту → резервування і довговічний намір → один зовнішній виклик → звірка → зафіксований факт. **Жорсткий контроль:** рядок наміру (`quota_reserved` і `send_started`) записують під блокуванням, перечитують за правилом 8, і безпосередньо перед єдиним викликом він має досі бути останнім рядком поточного сегмента, з `send_attempt_id` і SHA-256 маніфесту зі схвалення. Якщо запис або перечитування не вдалося: жодного виклику, нічого більше не записано, блокування збережено; якщо не вдалася лише ця перевірка останнього рядка: жодного виклику, а відкритий намір звіряють (4b). Кожен `send_attempt_id` має одного виконавця; повторний запуск звіряє наявну спробу. Пакет має один спосіб передачі (`agent_local_run`, `gmail_scheduled` або `manual_by_person`, DATA_CONTRACT.md §12.1).

**Види надсилання (F01).** `cv_submission`, `thank_you` і `ordinary_reply` (зокрема питання про період) мають кожен свій ключ повтору, який перевіряють у рядку, що починає надсилання: DATA_CONTRACT.md §4. Відкрита або невизначена спроба блокує повтор свого ключа і всі нові надсилання цієї людини.

Зовнішній виклик і локальний запис не можуть бути атомарними: після `send_started` ніхто не знає, чи викликано поштовий сервіс. Згода, відкликана до `send_started`, блокує надсилання; після нього надсилання звіряють, а не обіцяють, що його скасовано. Відсутність у SENT за неповної перевірки нічого не доводить.

### 6a. Gmail Scheduled через браузер агента (R03)

**Умови.** Режим це дозволяє, і людина особисто ввійшла в потрібний обліковий запис Gmail у браузері; агент ніколи не отримує паролів, одноразових кодів чи cookies, а сеанс може закінчитися будь-коли. Gmail надсилає заплановане повідомлення, навіть коли агент не працює, тож згоду, календар, пакет і резервування перевіряють до планування; зміна будь-чого з цього потребує нового схвалення, а для вже запланованого запису — спочатку перевіреної зміни чи скасування.

**Обмеження вбудованого браузера.** У задокументованій версії він не може завантажувати файли. Якщо це встановлення не може прикріпити схвалені файли, агент зупиняється до планування і використовує ручний шлях.

**Кроки і стани:** TODO_FOR_AI.md, частина C, «Gmail Scheduled через вбудований браузер (R03)» [Gmail Scheduled through the built-in browser], і DATA_CONTRACT.md §12.2. Невідомий результат — це подія `send_uncertain` (спосіб передачі `gmail_scheduled`); `schedule_uncertain` — лише назва цього стану. Ніколи другого повідомлення «про всяк випадок».

**Ручний запасний варіант.** Без браузера чи входу і без записаного наміру нічого не планують, а заявка переходить до TODO_FOR_AI.md, частина C, «Ручний запасний варіант для e-mail (R20)» [Manual email fallback] (`EMAIL_TO_SEND.txt`): людина надсилає або планує її вручну з того самого облікового запису (`manual_by_person`) і повідомляє про це; агент перевіряє це в Scheduled або SENT. Намір без перевіреного результату спочатку звіряють. Ручне планування використовує те саме єдине резервування.

### 6b. Повторне відтворення: перебудова подань (F04)

Кожен похідний файл (`registry.json`, черга, записи `Status.txt`, `quota.json`, `summary.js`, дані готовності і звітів) можна перебудувати з журналу і незмінних файлів; вихідні події та ідемпотентність: DATA_CONTRACT.md §3d. Повторне відтворення ніколи не змінює журнал.

1. Скопіюйте всі сегменти журналу в тимчасове місце; у журнал людини нічого не записується.
2. Перевірте кожен рядок: він розбирається, `sequence` не має пропусків між сегментами, жоден `event_id` чи `action_id` не повторюється з іншим вмістом (`INTEGRITY_CONFLICT`). Пошкоджений або неповний рядок зупиняє відтворення (`JOURNAL_DAMAGED`); жодне подання не записується.
3. Застосуйте події в порядку `sequence` (DATA_CONTRACT.md §3d): компанії і цілі, маршрути, пакети, плани і перенесення, скасування, резервування і квота, згоди, пошта і відповіді, статуси, архіви.
4. Побудуйте в тимчасовому місці: реєстр, чергу, записи `Status.txt`, `quota.json` (правило 7) і `summary.js` з його `source_revision`.
5. Файл, чий SHA-256 відрізняється від події, яка на нього посилається, позначає залежне подання як `INTEGRITY_CONFLICT`. Повторне відтворення не змінює квоти і саме не записує `approval_revoked`; агент записує `approval_revoked` новим рядком, коли це зачіпає схвалений пакет.
6. Замініть кожне подання, яке відрізняється (тимчасовий файл, перечитування, заміна). Проєкцію, яку не можна перебудувати, позначають як неповну, ніколи не вгадують.
7. Друге повторне відтворення з тієї самої ревізії нічого не змінює і не додає рядка журналу чи `Status.txt` для `event_id`, уже записаного.

Плани, пакети, копії в outbox і архіви ніколи не редагують. Виданий звіт ніколи не переписують: змінені числа отримують нову ревізію (`report_built`). Відсутню версію показують як «версія відсутня», а не відтворюють із пам'яті; відновлена копія (розділ 12) може її надати, якщо збігається контрольна сума. `quota.json` походить лише з подій; пошкоджений або відсутній файл замінюють результатом відтворення.

## 7. Можливості інструментів агента

Перевіреними вважаються лише платформи, названі в ACCEPTANCE_TESTS.md (Claude Code не підтверджено). Під час налаштування агент перевіряє кожну можливість: файлова система, вебпошук, пошук маршрутів, читання пошти, читання цілого ланцюжка, надсилання пошти, доказ надсилання (SENT), зображення і скани, відтворення DOCX, відтворення PDF, заплановане пробудження і блокування запису (`examples/workspace.example.json`). Він записує в `workspace.json` стан «доступно / недоступно / невідомо», час перевірки і, у своєму `note`, несекретну версію інструмента, якщо інструмент її повідомляє; рядок у файлі налаштувань не є доказом. У кожному чаті, який може надсилати, агент визначає поштовий обліковий запис і порівнює його з профілем, а також знову перевіряє поштові можливості, якщо їхня перевірка старша за 7 днів.

| Недоступно | Робота, яка може тривати |
|---|---|
| Gmail | Пошук, профіль, локальні пакети; поштова статистика позначена як неперевірена |
| Надсилання або доказ SENT | Чернетки і читання; автоматичні зовнішні дії вимкнено |
| Маршрути | Ціль залишається `route_unverified`; жодних тверджень щодо вимог до дороги |
| Відтворення документів | Чернетки збережено; візуальну перевірку не позначено як прийняту |
| Планування агента | Людина запускає чат вручну; черга залишається у файлах |

Для пошти агентові потрібно визначати обліковий запис, переглядати повідомлення сторінка за сторінкою, читати цілий ланцюжок, надсилати один раз і знаходити доказ надсилання; він повідомляє, що справді пропонують його інструменти. Ніщо, крім агента, не забезпечує місячний ліміт, тож заплановане автоматичне надсилання типово вимкнене і вмикається лише для профілю, людина якого це прийняла, після того як сценарії надсилання перевірено в середовищі цієї людини.

Журнал зберігає стан; галочка в Markdown нічого не доводить. Папка без `workspace.json` — нова: первинне налаштування — це TODO_FOR_AI.md, частина A, його позиція — `stage` у `workspace.json`. ## 9. Знімки, звіти і масштаб

Звіт рахують один раз, на фіксованій позиції журналу; DOCX/PDF і сторінка статистики мають однакові числа, `source_revision` і момент зрізу, а аналіз ринку не змінює жодного поштового підрахунку. Сторінка профілю показує власні заявки і спільну квоту людини. Агент записує лише `summary.js` (DATA_CONTRACT.md §9); сторінка — незмінна копія шаблону, яка не надсилає команд і не звертається до Gmail. Жодних індексів, черг чи фонових обробників не потрібно.

## 10. Зміни формату і межа першого випуску

**Позначки версій (кожне число має одне значення; інші документи посилаються на ці назви).**
- Версію документації визначає [VERSION](../../VERSION).
- `schema_version` знімка статистики (`summary.js`) — 1.4 (DATA_CONTRACT.md §9.1).
- `schema_version` налаштувань (`profile.json`) — 1.4, а `workspace.json` — 1.3 (`examples/settings.example.json`, `examples/workspace.example.json`); `schema_version` файлу `quota.json` — 1.3 (`examples/quota.example.json`).
- `format_version` файлу `workspace.json` — 1.4: структура файлу робочої папки (DATA_CONTRACT.md §1).
- `schema_version` рядка журналу — 1.2 (структура рядка, DATA_CONTRACT.md §3c); `registry.json` також використовує 1.2.

Число змінюється лише разом із власним форматом; нові назви подій додаються. Папки користувача ніколи не перезаписуються: міграція працює з окремою копією зі звітом, зберігає старі ідентифікатори і записи і потребує схвалення людини (журнал в одному файлі: «Застарілий журнал» [Legacy journal], DATA_CONTRACT.md §3d). Публічні приклади синтетичні.

Перше випробування — ручний прохід на синтетичних даних: профіль → ціль → пакет → план → імітована відповідь → звіт і офлайн-HTML; читання і надсилання Gmail — пізніше, а тести на перервану роботу і два паралельні чати — до будь-якого запланованого надсилання. Приймання потребує записаних доказів (ACCEPTANCE_TESTS.md).

## 11. Чотири мови, один проєкт

Англійська — основна; російська, німецька й українська — в `docs/ru`, `docs/de` і `docs/uk`, з одним договором даних, тими самими назвами подій і поведінкою; зміна правила оновлює всі чотири. Інтерфейс статистики підтримує `en`, `ru` і `de`; перемикання змінює лише підписи, а не записи чи окремо обрані мови резюме, листа, e-mail і звітів.

## 12. Локальні архіви і відновлення (R01)

Локальні архіви — це папки в `persons/<person_id>/archives/`, які записуються після кожної завершеної операції, щойно її факт є в журналі, а подання мають один спільний `source_revision`. Це резервні копії, ніколи не Gmail Archive, і вони ніколи не змінюють пошту. Коли, структура, маніфест, кроки запису (`backup_created`, `backup_failed`), строк зберігання, порушення цілісності (`ARCHIVE_INTEGRITY_FAILED`), відновлення в окрему копію і відновлення з Gmail після втрати всіх архівів (`RECOVERY_MODE`): DATA_CONTRACT.md §11.
