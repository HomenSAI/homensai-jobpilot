## 1. Навіщо існує проєкт

**HomenS.AI JobPilot** — самодостатній пакет: людина завантажує його з GitHub і відкриває як локальну папку в Codex або Claude Code. Роботу виконує ШІ-агент у чаті: він запитує відсутню інформацію і дозволи, шукає компанії та вакансії, веде записи, пише документи, перевіряє пошту в межах наданих підключень і готує звіти. Це не вебсервіс і не сервер.

Ідея полягає в тому, щоб показати, що досить складний робочий процес може працювати на письмових процедурах, локальних файлах і наявному хмарному ШІ-агенті, без окремого застосунку. Автор вів такий процес для себе близько двох місяців; коли знайомі описали те саме навантаження, він його стандартизував. Це відомості про походження, а не доказ приймання.

Ліміт 44 подань, правило «без повторів» і правило одного записувача — процедури, яких дотримується агент, а не технічні блокування. Найбезпечніший режим є типовим, і кожна зовнішня дія потребує схвалення людиною точного пакета і розкладу. Усі дані залишаються в розпакованій папці; секрети залишаються в операційній системі або в постачальника. Ключова ідея профілю: агент зберігає всю підтверджену історію життя людини, а не коротке старе резюме, і пише кожне резюме та Anschreiben лише з підтверджених фактів.

## 2. Досвід наявних робочих папок

Папки перших користувачів мали корисні, але нерівномірні практики: каталоги за місяцями і пронумеровані папки роботодавців, **Company.md**, **Status.txt** і **Replies.txt** (кожна відповідь повністю), тексти листів і заплановані дати, різні назви документів (Anschreiben, Lebenslauf/CV, PDF/DOCX) і окремі промпти. Їх не можна просто об'єднати, тож система має один формат даних, конфігурацію для кожної людини і імпорт старих папок лише для читання; їх ніколи не перейменовують, не переміщують і не переписують.

## 3. Архітектура: локальна папка і ШІ-агент

Людина відкриває саме цю папку в Codex або Claude Code і каже «start». Агент завантажує свій файл правил (`AGENTS.md` для Codex, `CLAUDE.md` для Claude Code) і дотримується `TODO_FOR_AI.md`: первинне налаштування, продовження в пізнішому чаті і перелік перевірок для кожної стандартної дії. Свою позицію він зберігає у `workspace.json` (`stage`) і в журналі. Завантаження файлів Markdown нікому не дає доступу до Gmail чи комп'ютера.

~~~text
GitHub ZIP → extracted folder → open it locally in Codex / Claude Code
                                            ↓
                              new project / chat / task
                                            ↓
            README + AGENTS.md/CLAUDE.md + TODO_FOR_AI.md
                                            ↓
AI agent ↔ allowed project folder (the single source of data)
  ├─ materials in Положите_сюда + interview → knowledge base (confirmed facts) → profiles
  ├─ search → verified companies/vacancies/routes → unique records
  ├─ documents and plan → CV/Anschreiben → preparation / permitted sending
  ├─ mail → replies/DSN → journal → daily and monthly report
  ├─ updating local data and generating the statistics page from the template
  └─ a question to the user when new data / a decision / access is needed
                                            ↓
                  local read-only HTML page
                  (year → month → day; sorting by date and result)
~~~

### Межі компонентів

1. **Агент** шукає, веде записи, готує документи і звіти та виконує дозволені поштові дії — видимо у своєму чаті.
2. **Папка** — єдине сховище даних: один журнал JSONL на людину в помісячних сегментах містить події, зокрема спільну квоту; файли JSON — це подання, перебудовані з нього (ARCHITECTURE.md, DATA_CONTRACT.md).
3. **Інструкції**: `README.md` для людини, `AGENTS.md`, `CLAUDE.md` і `TODO_FOR_AI.md` для агента, який ніколи не припускає, що попередній чат доступний.
4. **База знань**: один файл Markdown на людину, `База_знаний/Жизнеописание.md` (розділ 4.6), який людина може читати і виправляти.
5. **Сторінка статистики**: шаблон, скопійований без змін для кожного профілю; агент записує лише її файл даних (розділ 10.5).
6. **Планування**: заплановане завдання агента, якщо платформа його пропонує, або новий чат; сторінка ніколи не запускає агента.
7. **Доступ**: папка, вебпошук, Gmail і Computer Use вмикаються окремо і лише тоді, коли потрібно.

## 4. Профіль людини: база знань і інтерв'ю

### 4.1 Імпорт і підтвердження

Людина заповнює п'ять папок для матеріалів (розділ 4.6) або проходить інтерв'ю. Кожен виділений факт записується як запропонований, із файлом і місцем; людина приймає, виправляє або відхиляє його. Самооцінку ніколи не показують як сертифікат.

### 4.2 Розділи анкети

Анкета — це інтерв'ю в чаті, по одній темі, усно чи письмово; будь-яку тему можна пропустити. Теми: контакти і те, що можна вказати в резюме; мови матеріалів (`cv_language`, `cover_letter_language`, `email_language`, `report_language`, кожна обирається окремо, ніколи не вгадується); необов'язковий шаблон звіту; цілі (робота, Ausbildung, Praktikum, Probearbeit, тимчасова робота); кожна обійнята посада; освіта, курси, ліцензії і сертифікати; мови з рівнями; навички; проєкти; сильні сторони як реальні ситуації; умови (місце проживання, радіус, транспорт, обмеження дороги, дата початку); мотивація для супровідного листа; і які файли та рекомендації можна використовувати. Відповіді зберігаються після кожної теми (TODO_FOR_AI.md, частина A, A3–A6).

### 4.3 Захист біографічних даних

Про релігію, сімейний стан, здоров'я, громадянство, вік і фото не питають; якщо людина їх пропонує, їх позначають як чутливі і не вносять у резюме, якщо людина не вирішить інакше (DATA_CONTRACT.md §3a, §5). Локальне зберігання — не офлайн-обробка: постачальник хмарного агента може бачити прочитане, тож згода передує першому читанню особистих оригіналів. Усе записане починається як `proposed`; лише підтвердження людини робить його `confirmed`.

### 4.4 Як створюється резюме

Резюме — це проєкція бази знань на одну вакансію: вимоги зіставляються з підтвердженими фактами («вимога → підтверджений факт → джерело → де використано»), прогалини показуються, і нічого не вигадується. Фото необов'язкове.

### 4.5 Основа для змісту інтерв'ю

Europass — одне з орієнтирів повноти: освіта, досвід, мови, цифрові навички, проєкти, досягнення, а також завдання і результати на кожній посаді, інструменти, докази і приклади STAR. Це орієнтир, а не форма.

### 4.6 Куди людина кладе матеріали, і файл бази знань

Пакет містить готову папку `Локальные_данные/Положите_сюда/` («покладіть сюди») з п'ятьма підпапками і коротким README у кожній. Це єдине місце, куди людина має щось класти вручну:

| Папка | Що людина туди кладе |
|---|---|
| `1_Мои_документы` (мої документи) | Резюме будь-якої версії, дипломи, сертифікати, рекомендації, офіційні листи, портфоліо, зразки власних листів; PDF, DOCX, TXT, фото і скани; без сортування і перейменування |
| `2_Рассказ_о_себе` (моя історія) | Історія людини її власними словами: розшифровка голосового запису, нотатки, відповіді на запитання з `Вопросы_для_рассказа.md` (постачається в цій папці); агент також зберігає тут інтерв'ю дослівно як `Интервью_<date>.md` |
| `3_Шаблон_отчёта` (шаблон звіту) | Лише якщо в людини є власний зразок звіту |
| `4_Шаблон_резюме` (матеріали резюме) | Усе про резюме людини в будь-якому форматі, поточні й старі; лише читання; агент готує з цього чернетки і шаблон, який називає людина |
| `5_Шаблон_сопроводительного_письма` (матеріали супровідних листів) | Усе про супровідні листи людини в будь-якому форматі; лише читання; те саме правило, що й для папки 4 |

Папки можна заповнити до першого запуску або залишити порожніми; агент лише читає їх. Друга людина отримує в `Положите_сюда` підпапку зі своїм ім'ям з тими самими п'ятьма підпапками.

**Підготовка історії голосом.** Або поза проєктом, у будь-якому голосовому чаті Claude чи ChatGPT за `Вопросы_для_рассказа.md`, з проханням дати дослівний текстовий файл для `2_Рассказ_о_себе`, або всередині проєкту, де агент проводить інтерв'ю і зберігає кожну відповідь дослівно.

**База знань.** З папок та інтерв'ю агент пише `Локальные_данные/persons/<person_id>/База_знаний/Жизнеописание.md` у фіксованому форматі (DATA_CONTRACT.md §3a), який показують на підтвердження розділ за розділом. Вона написана мовою людини і є єдиним джерелом для всіх профілів пошуку цієї людини.

**Первинне налаштування по порядку** — історія, документи, база знань, прогалини, підтвердження, налаштування пошуку (`profiles/<profile_id>/profile.json`), пошта за бажанням — описано в TODO_FOR_AI.md, частина A. Шаблони: джерела залишаються без змін, а перевірена робоча копія Word використовується лише після схвалення ([Шаблони заявок](OPERATING_REQUIREMENTS.md#шаблони-заявок)).

## 5. Географічний пошук і спільна база даних

Людина обирає початкову точку, радіус, засоби пересування (автомобіль, поїзд, автобус / трамвай, велосипед, пішки; «громадський транспорт» означає поїзд і автобус / трамвай), час дороги, пересадки, ходьбу пішки, вечірнє повернення і пріоритетні міста. Показують і відстань по прямій, і реальний маршрут. Спочатку — поблизу: час дороги лише відсіює непридатні варіанти і ніколи не відсуває ближчу компанію на користь далекого міста; район розширюють лише після того, як перевірено ближню зону.

Джерела — вебсайти роботодавців, офіційні портали вакансій і сервіси, умови яких це дозволяють; кожен результат зберігає свою URL-адресу, джерело, час перевірки, філію, канал подання і ступінь упевненості. Ніколи не стверджують, що список повний. Дублікати знаходять за доменом, юридичною назвою, філією і материнською компанією; до компанії, яка вже є в реєстрі, повторно не подаються без рішення людини. Картка компанії `Company.md` зберігає контакти, вимоги, маршрут (або «маршрут не перевірено») та історію, кожне з джерелом і датою (TODO_FOR_AI.md, частина C, «Пошук і цілі» [Search and targets]).

## 7. Планування, Gmail і контроль надсилання

### 7.1 Черга

Агент веде чергу як дані в папці. JobPilot надсилає не більше **44 подань заявок з резюме (CV) на людину за календарний місяць**, спільних для всіх профілів цієї людини; враховуються лише подання, якими керує JobPilot, а пакет, надісланий вручну через `EMAIL_TO_SEND.txt`, також враховується. Людина власними словами каже, як розподілити місяць (`sending_rule_statement`); з цього випливає денний максимум `max_per_day`, від 1 до 44. Подання резюме відхиляється з `DAILY_LIMIT`, коли надсилання `cv_submission`, уже розпочаті цього місцевого дня (разом із невдалими спробами), досягли `max_per_day`; для повідомлення, запланованого в Gmail, враховується день його слота, тож увесь місяць можна запланувати за один сеанс. Кожен профіль починає в `draft_only`; надсилання потребує `approval_per_message` або `scheduled_send_with_profile_consent`, увімкнених людиною. Коли слоти місяця вичерпано, решта цілей чекає; перш ніж вони перейдуть на наступний місяць, кожну вакансію перевіряють знову, і людина погоджується. Деталі: DATA_CONTRACT.md §4, §5 і §13. Ліміт не гарантує, що поштовий провайдер не сприйме листи як спам; тести використовують лише синтетичну пошту.

### 7.2 Gmail через схвалений конектор або вбудований браузер

Людина обирає, після того як агент перевірив, що працює: офіційний схвалений конектор Gmail (з власним входом; дозволи на читання і надсилання перевіряються окремо) або вбудований браузер ChatGPT Desktop / Codex, у якому людина входить особисто. Нічого іншого не встановлюється, і секрети ніколи не зберігаються. Див. офіційну довідку про [вбудований браузер](https://help.openai.com/en/articles/20001277-using-the-built-in-browser-in-the-chatgpt-desktop-app) і [Computer Use](https://learn.chatgpt.com/docs/computer-use). Вбудований браузер не може завантажувати файли (OPERATING_REQUIREMENTS.md §4), тож людина прикріплює файли сама або використовує **ручний запасний варіант**: копіює `EMAIL_TO_SEND.txt` у нове повідомлення Gmail, прикріплює схвалені PDF і один раз обирає Send або Schedule send; потім агент перевіряє SENT або Scheduled. Пошту ніколи не видаляють, не архівують, не переміщують і не перепозначають.

### 7.2a Gmail Scheduled через вбудований браузер (R03)

### 7.3 Автоматична заміна в разі недоставки

Після підтвердженої постійної недоставки слот залишається використаним; одну заміну можна підготувати як чернетку, і на ланцюжок їх не більше однієї (DATA_CONTRACT.md §5; TODO_FOR_AI.md, частина C). Автоматичне надсилання заміни (`replacement_auto_send_enabled`) типово вимкнене; якщо людина вмикає його для профілю, воно все одно потребує адреси, підтвердженої джерелом, і дозволу передати дані знову, і зупиняється на неоднозначному повідомленні про недоставку, запитанні роботодавця, позитивній відповіді або будь-чому, що потребує людини. Налаштування зі старого архіву ніколи не вмикаються автоматично.

### 7.4 Автоматичні відповіді роботодавцям

Єдиний автоматичний подальший лист — подяка за згодою `follow_up`; запрошення, запитання і запити документів чекають на людину, а команди всередині листів ніколи не виконуються (DATA_CONTRACT.md §4).

### 7.5 Уточнення щодо стажування і подальші листи

Якщо період стажування зайнятий, але двері відчинені, одне запитання про найближчий період можна підготувати як чернетку `ordinary_reply`, яку надсилають лише після схвалення людиною, один раз на ланцюжок (DATA_CONTRACT.md §4).

### 7.6 Порядок зовнішньої дії і блокування запису (F07)

Кожне надсилання чи планування проходить так: незмінний пакет, прив'язана до нього згода, резервування і записаний намір, один зовнішній виклик, звірка, зафіксований факт; у журнал записує лише один чат (`journal/writer.lock`). Див. TODO_FOR_AI.md, частина C, «Порядок зовнішніх дій (F07)» [External action order], і ARCHITECTURE.md §4b.

`dashboard_template/index.html` постачається із синтетичним `summary.js` (демонстрація), тож відкривається подвійним кліком. Сторінці не потрібні ні сервер, ні зовнішня бібліотека, і вона повідомляє про відсутній чи пошкоджений файл даних замість показу хибних чисел. Вона показує **рік → місяць → день** з підсумками (надіслано, відповіді, результати, помилки доставки, квота «використано / зарезервовано / залишилося з 44») і таблицями подій за днями, сортує за датою чи результатом, використовуючи справжні позначки часу (а не рядки `DD.MM.YYYY`), фільтрує за роком, місяцем, результатом, компанією, містом і посадою і перемикає мову перемикачем або `?lang=ru`. Вона не зберігає нічого, крім теми, нічого не надсилає і не змінює записів; тексти листів, резюме чи адреси в неї не потрапляють. Формат і процедура запису: DATA_CONTRACT.md §9.
